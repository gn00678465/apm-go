# apm-go architecture

How apm-go is built: the layers, the direction dependencies may point, the data flow of each major command, the cross-cutting mechanisms every layer shares, and the gates a change must pass. Every structural claim is anchored to code as `path:line`. Product facts and the terminal UI design live in [PRODUCT.md](PRODUCT.md); engineering and testing rules live in [AGENTS.md](AGENTS.md). Each topic lives in exactly one of the three files.

Layout: `cmd/apm-go/` holds one file per cobra subcommand; `internal/` holds the libraries listed in §2; `tools/parity/` is the output-contract runner (§5); `spec/conformance/` holds spec tables that tests read at run time.

Leaves (import nothing in-module): `archive`, `credsec`, `experimental`, `pack`, `rootfs`, `security`, `semver`, `ux`, `version`, `yamlcore`.

**Dependency rules.** A new edge that the graph lacks is a design change; get a ruling before adding it.

- `yamlcore` is the floor for all YAML and depends only on `go.yaml.in/yaml/v4`; `manifest` depends only on `yamlcore`; `lockfile` only on `manifest` and `yamlcore`.
- `deploy` reads only what is already on disk under `apm_modules/`; fetching (`gitops`, `registry`) stays above it. `resolver` fetches through the injected `resolver.PackageLoader` interface (`internal/resolver/types.go:24`), which keeps `gitops` out of it.
- Terminal output is emitted by `cmd/apm-go`, `pack/bundle`, and `pack/pluginmanifest`; every other package returns diagnostics or errors for the command layer to print.
- `security` has two callers: `pack/bundle` and `cmd/apm-go/audit_content.go` (§4).

## 3. Data flows

### 3.1 `apm-go install`

```mermaid
sequenceDiagram
  participant C as cmd/apm-go/install.go
  participant M as manifest
  participant R as resolver
  participant L as registry.Loader → gitops.RealPackageLoader
  participant D as deploy
  participant K as lockfile
  C->>C: frozen? (flag or CI) install.go:263
  C->>M: yamlcore.SafeLoad + ParseManifest install.go:338
  C->>K: ParseLockfile install.go:674
  alt frozen
    C->>K: checkFrozenManifestSync :685 / planFrozenDeploy :705 (VerifyDeployedState)
    C->>L: registry: VerifyArchiveBytes :770 + archive.SafeExtract :773
    C->>D: locked files not on disk: frozenDeployPlan.run :878 → deploy.Run in a temporary directory, then in place; no lock write
  else resolve
    C->>R: Resolve(m, lock, tags, regLoader, cfg) install.go:972
    R->>L: PackageLoader.LoadPackage
    L-->>L: registry dep: HTTP download → hash check → SafeExtract loader.go:48
    L-->>L: otherwise: clone under ApplyCloneEnv clone.go:39
  end
  C->>D: ResolveTargets :1981 → deploy.Run :2055
  D->>D: Adapters[target] deploy.go:520
  C->>K: buildLockfile :1776 → installRun.finish install_report.go:410 (IsSemanticEqual + lockIsCanonical :422 → WriteLockfile :425 → writeLockfileBytes :429)
```

1. `installCmd` assembles `installDeps` (`cmd/apm-go/install.go:38`): `tags` is `gitops.RealTagLister`, `loader` is `gitops.RealPackageLoader` (`:179-180`). Tests inject both.
2. `runInstall` (`:231`) decides frozen first; with no flag and `lockfile.IsCIEnvironment()` true it forces frozen and prints an info line (`:249-252`). A frozen install with no `apm.yml`, `--global` included, goes on with an empty manifest and creates no file (`:303`). First, `checkFrozenManifestSync` (`cmd/apm-go/install_frozen_sync.go:25`, called at `install.go:685`) refuses a lock that no longer pins what `apm.yml` declares, the Oracle's `lockfile_satisfies_manifest` (`install/plan.py:453-506`), which its `--frozen` runs before it resolves (`install/service.py:300-353`): for each direct dependency, regular and dev, that is not local, under the key `refUniqueKey` gives it (`:100`, the Oracle's `get_unique_key()`, with the host when it is not github.com), a missing entry, a full 40-hex ref other than the entry's `resolved_commit`, or a change `lockedRefChanged` finds (`:70`, the Oracle's `detect_ref_change`, `drift.py:95-195`, which `shouldFetch` uses too) is one reason line, and the install ends with exit 1 before anything is fetched or written. Then `checkInsecureDirect` (`install.go:688`) runs the HTTP policy of the direct dependencies (step 4), and `useLockedAliases` (`install_frozen_deploy.go:265`, called at `install.go:693`) gives each direct dependency the alias its lock entry records, so the packages are read from the directories the lock has them in, also when the lock an earlier apm-go wrote records no alias that `apm.yml` declares. Then, before any check of the deployed files, fetch or write, `checkFrozenCommitPins` (`cmd/apm-go/install_frozen_commit.go:19`, called at `install.go:694`) refuses a git entry whose `resolved_ref` names a commit (`gitops.IsCommitRef`) and whose `resolved_commit` does not start with it, the Oracle's `_check_locked` (`deps/immutable_requirements.py:116-140`), naming the chain of `resolved_by` up to the root's name (`frozenChain` `:44`). A frozen install checks the deployed files with `lockfile.VerifyDeployedState` under the deploy root (`deployDir`, which is `HOME` for `--global`; `.` otherwise) and reports the first violation, which is fixed because the violations are ordered by `lock.Dependencies`, then local content, each by ascending path. A locked file is not on disk when its violation has no observed hash and `os.Lstat` finds nothing at the path; a file with other content, a dangling symlink, an unreadable file and a directory are the other kind, and the first of those in that order is the error, with nothing written (`planFrozenDeploy` `cmd/apm-go/install_frozen_deploy.go:53`, called at `install.go:705`). When every violation is a file that is not on disk, the frozen install deploys from the lock (issue #65). Before any write or network request the plan needs an `apm.yml`, a target (`deploy.ResolveTargets`; none is `errNoDeployTarget`, exit 2), and for each such path a target that governs it in the bucket that records it (`frozenTargetsGovern` `install_frozen_deploy.go:95`, `deploy.TargetsGovernPath`); without `apm.yml`, or for a path no target governs, the error is the `<missing>` violation of that path. After the source steps (A2) and (B), `frozenDeployPlan.run` (`install_frozen_deploy.go:114`, called at `install.go:878`) copies each local-path direct dependency that has no `apm_modules/<key>` through the loader and builds the `resolver.ResolutionResult` from the lock's dependencies. It then tries the deploy in a temporary directory, which it removes when it returns: `deploy.Run` with that directory as the deploy directory and every other argument as the deploy in place has it (`:151`), so a `--global` trial is a symlink deploy too: a symlink deploy records the symlinks inside a skill's source directory, which a copy deploy skips. The links of a trial point at the sources, and removing the directory removes the links only. Each hash the trial returns has to be the lock's hash for that path in the same bucket (`frozenDeployMatchesLock` `install_frozen_deploy.go:213`; the digests are compared as `VerifyDeployedState` compares them, so a lock with a bare hex digest matches): another hash, or a path the lock does not have (`expected <not in lockfile>`), is a content-integrity error, so sources that changed after the lock was written fail the install; and each locked path that is not on disk has to be among the trial's paths of the bucket that records it (`missingDeployed` `install_frozen_deploy.go:188`), else the error is its `<missing>` violation. A frozen install that fails up to here leaves every path under the deploy root outside `apm_modules/` as it was; the sources this run put in `apm_modules/` stay, as step (B) leaves them. Only then `deploy.Run` runs in place as `deployAndFinalize` calls it (`:163`), `frozenDeployMatchesLock` runs on its result, and `VerifyDeployedState` runs once more. This path writes neither the lock nor `apm.yml` nor `.gitignore`, cleans no stale file, and prints only the frozen success line. `deploy.Run` writes a merged MCP config such as `.mcp.json` as it always does; that file is not verified. Deliberate deviation from the Oracle, whose `--frozen` checks the lock's structure and then runs an ordinary install (`commands/install.py:1758-1762`): it overwrites a changed deployed file and rewrites the lock when the sources changed. Its source step (B) calls the loader for git dependencies only, with a reference rebuilt from the lock entry; the reference of an entry with a `virtual_path` carries the `VirtualType` that parsing `apm.yml` gives that path (`manifest.VirtualTypeOf` `internal/manifest/depref.go:1600`, set at `:793`), because the loader takes only that directory for a subdirectory reference and the whole repository for a reference with no type. The rebuilt reference has no `Scheme`: the lock does not record one. The ref it passes is the entry's `resolved_commit`, so a subdirectory package is cloned at the commit the lock pins. (B) then verifies `tree_sha256` in the entry's directory below `apm_modules/` for each git entry with a commit and a `tree_sha256`, except a subdirectory package (`:868`), whose directory is not a checkout; an entry with none, a subdirectory package's or any of a lock the Oracle wrote, which has no such field, is pinned by `resolved_commit` and `deployed_file_hashes` alone (issue #151). a lock entry whose key starts with `_local/` (`localModulesKeyPrefix` `:3494`, a local-path dependency) is skipped like a `registry` or `local` source (`:770-777`). The current lock records a local package as `source: local`; the key check is for a lock written before issue #50, which records it as a git source with no source path, so the loader would delete the copy and clone it as a git dependency. Such a lock names the package `_local/<name>-<8 hex>` (`legacyLocalModulesKey` `:3443`). ### 3.6 `apm-go self-update`

1. `selfUpdateCmd` (`cmd/apm-go/self_update.go:20`) creates the cobra command with `--check`.
2. `runSelfUpdate` (`:42`) creates a `selfupdate.Updater` and calls `CheckLatest` with a 30s context timeout.
3. `CheckLatest` (`internal/selfupdate/selfupdate.go:63`) guards `version.Version == "dev"`, then queries `https://api.github.com/repos/{repo}/releases/latest` (excludes pre-releases by API design) and compares versions via `semver.CompareVersions`.
4. If `--check` is set, the command prints the result and exits.
5. Otherwise, `Apply` (`:86`) downloads `SHA256SUMS`, resolves the path of the running binary, and downloads the platform asset (`PlatformAssetName` `:252`) into a temporary file `.apm-go-self-update-*` in the binary's own directory (`os.CreateTemp`, `:115`), so a directory the user cannot write fails before the download, with the directory named in the error. It verifies the hash and calls `replaceBinary` (`replace.go:22`), which replaces the binary within that directory, so the update does not depend on the file system `$TMPDIR` is on (issue #83: a `/tmp` on tmpfs made the rename fail with `EXDEV`). The temporary file is removed on every path. On Windows, the running binary is renamed to `.old` before the new one is written; on Unix, the new binary is made `0755` and `os.Rename` replaces the inode directly. The download timeout is 5 minutes.
6. Progress is reported through `Updater.OnProgress`, which the command wires to `ux.Spinner.Update` with a human-readable byte counter.

This is an apm-go-only command with no Oracle equivalent.
