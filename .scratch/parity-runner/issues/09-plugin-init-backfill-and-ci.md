## Investigation findings (read before touching the fixtures)

- **Project-name argument is required for a deterministic tree.** `plugin init [PROJECT-NAME]` with no name uses the CWD's own basename for `name:`/directory scoping; since each side runs in its OWN randomly-named sandbox, an unnamed run would make `apm.yml`'s `name:` field (and the created-file path itself) differ between sides for reasons having nothing to do with the product. Every case below passes an explicit `plugin-init-fixture` project-name argument.
- **`GIT_CONFIG_GLOBAL` needs no new runner mechanism.** The existing `case.env` + `<TMP>` placeholder (expands to the run's own sandbox cwd) is enough: each case's `fixture/.gitconfig-fixture` is materialised into cwd alongside any other fixture files, and `"GIT_CONFIG_GLOBAL": "<TMP>/.gitconfig-fixture"` points both sides' `git config user.name` lookup at the identical fixed value. Verified this fixture file itself never appears as a spurious tree diff (tree diffing compares each side's own before/after DELTA, not raw absolute trees — a fixture file identical on both sides before either binary runs is invisible to it).
- **`normalise-upper` is NOT actually an Oracle-rejects/apm-go-accepts case, contrary to the ticket's original assumption.** Verified live: the pinned Oracle's `--format` is a Click `Choice(..., case_sensitive=False)`, so `--format AGENT-PLUGIN` (uppercase, hyphen-separated) is accepted by the Oracle exactly as it is by apm-go's own `normalizeBundleFormatKey`. Only `normalise-underscore` (`agent_plugin`) and `normalise-space` (`agent plugin`) actually change the SEPARATOR, which Click's Choice rejects outright (before its own internal `coerce_bundle_format` normalization — which WOULD accept it — ever runs, since Click validates the raw token against the literal choice list first) while apm-go's shared resolver (ticket 04) accepts. `plugin-init-normalise-upper` is waived under the same F01 rendering/channel/apm.yml-comment mechanism as every other success case, not F12 — only `normalise-underscore`/`normalise-space` are the two genuine F12 "spec-over-Oracle" waivers.
- **Two byte-exact wins, one real (but out-of-scope) apm.yml gap.** `plugin.json` (all formats, including agent-plugin's `$schema`/`extensions` and unicode-author's `ensure_ascii`-equivalent `\uXXXX`/surrogate-pair encoding) and `mcp.json` (agent-plugin mode) are byte-for-byte identical to the Oracle's own output on every case tested, with no waiver needed for either file. `apm.yml` is NOT: the Oracle's PyYAML-rendered comment block above `# targets:` reads differently from apm-go's own (4 lines naming `--target`/resolution-order/accepted-values vs the Oracle's 2-line block with a commented-out example list), and — unicode-author only — a non-ASCII `author:` value is double-quoted with `\U`-escapes by apm-go's YAML emitter vs left as bare literal UTF-8 by the Oracle's. Both real, pre-existing, out-of-scope findings, spun into `.scratch/parity-runner/issues/19-plugin-init-output-surface-gaps.md` (finding 1) rather than fixed inline. Every case that writes `apm.yml` (11 of them) carries a `tree_paths: ["cwd/plugin-init-fixture/apm.yml"]` waiver for exactly this.
- **`init`/`plugin init`'s plain success path splits across stdout AND stderr, unlike the Oracle's single-stream stdout output.** The Oracle's `logger.success()`/`.progress()` always render on stdout (its Console defaults there). apm-go's `runInitCore` Phase 7 has the SAME split for ALL non-clack (`--yes`, or non-interactive) runs: `ux.Info(os.Stderr, ...)` (the three next-steps bullet lines) correctly redirects to stdout via `oracleLine`'s `errWriter`, but `ux.Success(os.Stderr, ...)` and `ux.Section(os.Stderr, "Next steps")` do NOT (`Success`/`Section` don't route through `oracleLine`) — so the success title and "Next steps" header stay on stderr while the bullet lines land on stdout. Investigated whether this is a latent bug to fix (ticket 08's own precedent) or a deliberate, pre-existing design choice: `cmd/apm-go/init_clack_test.go`'s own `captureStderr` doc comment states this is intentional ("init writes its human-facing output straight to os.Stderr (the stream contract in terminal-ux-contract §3)", a doc not currently in the tree to consult further) — reversing a documented design decision is a real design question, not a ticket-09-sized fix, especially for the LAST ticket before a release. Spun into ticket 19 (finding 2) instead. Every success case carries this as part of its combined `stdout`+`stderr` waiver.
- **`existing-pluginjson-no-yes`'s wording differs, but the invariant (refused, file intact) holds on both sides.** Live-captured: with an empty stdin (matching the runner's own `strings.NewReader("")` for a case with no `stdin` set) and no `--yes`, the pinned Oracle unconditionally calls `click.confirm(...)` (no TTY check at all — `commands/init.py:212`), prints its prompt to stdout, hits immediate EOF, and aborts with a message-less exception rendered as `Error initializing project: `. apm-go checks `ux.CanPrompt()` up front (false in this sandbox) and refuses immediately with its own descriptive message. Both: exit 1, `plugin.json` left byte-identical (verified: `tree` shows no diff at all). Waived `stdout`+`error_body`, F08 (behavioral wording difference in non-interactive detection, not a bug).
- **`help_semantic`'s `--format`-flag gap is a pre-existing runner-parser limitation, not a new product gap.** `tools/parity/help_semantic.go`'s `parseHelpFlags` only captures a flag description's first physical line; when Click/Cobra wrap a long description (or, as here, a long choice-list metavar pushes the description onto an entirely separate continuation line), the flag is truncated or dropped. Verified this is not new to this ticket: `pack-help`'s own (already unwaived, ticket-17-tracked) `help_semantic` diff shows the identical pattern on its own long flag descriptions. Spun into ticket 19 (finding 3) as cross-cutting tooling work; `plugin-init-help` is waived (`stdout`+`help_semantic`, F01) citing this directly.
- **`go test ./...` needed one fix to be a meaningful, always-green CI gate.** `TestParseDepString_AbsolutePath` (`internal/manifest`) mixes 4 platform-independent subtests with 2 windows-drive-letter-only subtests in one table; only the latter 2 ever failed on Linux (verified: `windows_UNC` and all 3 POSIX subtests already passed). Added a `winOnly`-gated `t.Skip` on just those 2, so the CI `go-test` job is genuinely green rather than permanently red from a pre-existing, already-documented (AGENTS.md) platform gap. `AGENTS.md`'s own note updated to match, plus the ticket's required one-sentence "go test ≠ parity gate" note under Testing patterns.
