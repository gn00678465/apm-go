## Work Package WP01: Validator core — rule table, five checks, Report model (Priority: P1)

**Goal**: A pure function `Validate(data []byte) Report` in `internal/pluginjson` that runs Structure, Name, Fields, Paths, and Unrecognized checks against a rule table, producing the `Finding`/`Report` shapes `data-model.md` defines.
**Independent Test**: `go test ./internal/pluginjson/ -run TestValidate` is green with one subtest per spec.md acceptance scenario/edge case that IC-01 covers (Structure, Name, Fields, Paths, Unrecognized).
**Prompt**: `tasks/WP01-validator-core.md`
**Requirement Refs**: FR-003, FR-004, FR-005, FR-006, FR-007, NFR-002, NFR-003, C-004

### Included Subtasks

T001 [P] Define `Finding`, `Report`, `Rule` types and the rule table skeleton with `Source` tags (`schema` / `docs` / `apm-go`) in `internal/pluginjson/validate.go`
T002 Implement the Structure check: 5 MiB cap (size passed in, not re-stat'd here), `utf8.Valid`, JSON decode via `map[string]json.RawMessage`, top-level-object check, duplicate-key detection via a `json.Decoder` token scan
T003 Implement the Name check: missing/non-string/empty/whitespace/control-character/bidi-character errors, non-kebab-case warning
T004 Implement the Fields type check for every rule `Kind` (string / object / bool / array-of-string / string-or-array / string-array-or-object / dependency-list), the `metadata`/`experimental` warning downgrade, `author.*`, `dependencies[i]`, and `experimental.<k>` sub-checks
T005 Implement the Paths syntax check (`./` prefix required, absolute rejected, `..` segment rejected) for every path-typed field and each element of a path-typed array
T006 Implement the Unrecognized check: top-level and `experimental.*` keys outside the known set, Damerau-Levenshtein ≤ 2 suggestion, `themes`/`monitors` "belongs under 'experimental'" warning
T007 Write `internal/pluginjson/validate_test.go`: one table-driven subtest per spec.md acceptance scenario (US1 AS1–AS8, US2 AS1–AS5, US3 AS1–AS5) and per edge case, named after the scenario

### Implementation Notes

- Write T007's tests first against the T001 type skeleton, observe RED, then implement T002–T006 to turn them GREEN one check at a time — this is the WP's own TDD cycle (plan.md Charter Check row 3).
- Keep `Validate` a pure function: no `os`, no filesystem access in this file. `internal/pack/bundle` stays the only import.
- Annotate every rule table entry's `Source` field per data-model.md's invariants so WP02's schema-sync test can assert against it mechanically.

### Parallel Opportunities

- T001 can start immediately; T002–T006 are independent checks over disjoint code paths and can be built in any order once T001 lands, but each depends on T001's types.

### Dependencies

- None (foundational package).

### Risks & Mitigations

- Deep nesting / large inputs: `encoding/json`'s own recursion limit returns an error, never panics — verified by WP02's fuzz test, not re-derived here.
- Duplicate-key detection must not double-decode the value; use the token stream only for key order/duplicates, and `map[string]json.RawMessage` for values (data-model.md).

**Prompt**: `tasks/WP02-hardening-evidence.md`
**Requirement Refs**: NFR-002, NFR-004, C-004, SC-002, SC-003

### Included Subtasks

T010 [P] Write `internal/pluginjson/validate_property_test.go`: a `testing/quick` generator that emits objects built only from known fields with correct types (≥ 100 iterations), asserting `Validate` returns zero findings (NFR-004)

- Follow `internal/pack/bundle/schema_sync_test.go`'s naming and structural conventions (`schemaDoc`, `schemaPropsAndRequired`, fail-closed unknown-keyword checks) for T009 rather than inventing new helper shapes; this package has no shared test-helper package with `bundle`, so duplicate only what's needed, as that file's own doc comments do.
- T010's generator must only ever emit already-known field names — the point of the property test is "zero false positives on legitimate input," not fuzz coverage (that is T011's job).

### Parallel Opportunities

### Dependencies

- Depends on WP01 (needs `Validate`, `Report`, and the rule table's `Source`/`IsPath` fields).

### Risks & Mitigations

- Schema drift after vendoring: T009 is the anti-drift guard itself; a future schema update failing T009 is the intended signal, not a bug.
- Fuzz false negatives from a weak seed corpus: T011's seed list is enumerated directly from spec.md's User Story 3 acceptance scenarios, not invented ad hoc.

## Work Package WP03: CLI subcommand — locate, render, exit codes (Priority: P1) 🎯 MVP

**Goal**: `apm-go plugin validate [path] [--strict] [-v]` wired into `cmd/apm-go`: manifest location (upstream `find_plugin_json` order), rendering matching `contracts/cli-plugin-validate.md` byte-for-byte, `--strict`/`-v` flags, and exit 0/1/2.
**Independent Test**: `quickstart.md`'s three manual scenarios (clean scaffold, typo field, broken manifest) reproduce exactly; `go test ./cmd/apm-go/ -run TestPluginValidate` is green.
**Prompt**: `tasks/WP03-cli-subcommand.md`
**Requirement Refs**: FR-001, FR-002, FR-008, FR-009, FR-010, FR-011, FR-012, NFR-001, NFR-003, NFR-005, C-003

### Included Subtasks

T013 Implement manifest location in `cmd/apm-go/plugin_validate.go`: directory vs. file dispatch, the four-candidate probe order (duplicated locally with a doc comment citing `internal/pack/bundle/producer.go`'s `pluginJSONCandidates` as the source of truth — no new cross-package export, per C-002), `Lstat`-based 5 MiB cap enforced before any read, and the "no plugin.json found" message
T014 Implement result rendering in `plugin_validate.go`: the `Validating plugin '<path>'...` progress line, the optional `-v` known-fields listing, per-check `passed`/finding lines (errors before warnings within a check), and the `Summary: N passed, N warnings, N errors` line — using `ux.Progress`/`ux.Info`/`ux.Success`/`ux.Warn`/`ux.Error` only, matching `contracts/cli-plugin-validate.md`'s exact message strings
T015 Implement `--strict` and exit-code wiring: exit 0/1 via `withSilentExitCode`, positional-arg-count and unknown-flag usage errors via `withUsageError` (exit 2), matching the exit table in `contracts/cli-plugin-validate.md`
T016 Wire `pluginValidateCmd()` into `cmd/apm-go/plugin.go`'s `pluginCmd()` (`AddCommand`) and rewrite its "exactly one child" deviation comment (C-005) to record issue #13 and this mission instead
T017 Write `cmd/apm-go/plugin_validate_test.go`: one cobra end-to-end subtest per spec.md acceptance scenario (US1 AS1–AS8, US2 AS1–AS5, US3 AS1–AS5), a `--help` test (`plugin --help` lists `init`+`validate`; `plugin validate --help` documents `--strict`/`-v`), and a read-only snapshot test asserting the target directory's file tree and every file's bytes are unchanged before/after validation (NFR-001)

### Implementation Notes

- T013–T015 build the command in locate → render → exit-code order, matching the state-transition list in `data-model.md`'s final section.
- `-v` output happens before `Validation Results:` even when Structure fails, per data-model.md's `KnownFieldsPresent` field being independent of `StructureFailed`.
- Symlink handling (NFR-003): `Lstat` the selected candidate; do not follow a symlink whose target lies outside `path`.

### Parallel Opportunities

- T016 (one-line `AddCommand` + comment rewrite) can happen any time after T013 exists; T017 should follow T013–T015 so its RED tests observe real failures against the real command.

### Dependencies

- Depends on WP01 (needs `Report`/`Finding` to render).

### Risks & Mitigations

- Exit code mapping is the highest-risk area (three exit codes, four trigger conditions) — T017's scenario tests are the primary defense; cross-check every exit value against `contracts/cli-plugin-validate.md`'s table directly, not from memory.
- `cobra.MaximumNArgs`'s default parse error must be mapped to `withUsageError` explicitly (T015), or extra positional args will exit 1 instead of the contracted 2.
