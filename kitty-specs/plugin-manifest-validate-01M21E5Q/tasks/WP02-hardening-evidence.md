### Subtask T009 [P] -- validate_schema_sync_test.go

- **Purpose**: Make C-004's field-source rule mechanically checked, not just documented in a comment.
- **Steps**:
  1. Load and parse the vendored schema (T008) into a generic `map[string]any` tree (plain `encoding/json`, no schema library needed for structural inspection).
  2. Extract the schema's top-level `properties` key set.
  3. Extract every top-level property whose own node has `"pattern": "^\\./"` (a plain string match on the pattern value is sufficient; do not build a full JSON-Schema-pattern interpreter) -- this is the schema's own path-field marker.
  4. Assert: `{r.Name | r.Source == sourceSchema}` from WP01's rule table (imported directly -- this test file lives in the same package, `package pluginjson`, so it can read the unexported rule table variable directly) is a **superset** of the schema's `properties` key set (not necessarily equal -- WP01's table also has `docs`- and `apm-go`-sourced fields the schema doesn't know about).
  5. Assert: `{r.Name | r.IsPath}` from the rule table equals exactly (not superset) the schema's `^\./`-pattern field set, unioned with the three doc-only path fields `{"workflows", "experimental.themes", "experimental.monitors"}` -- use a symmetric-difference helper (mirror `internal/pack/bundle/schema_sync_test.go`'s `assertFieldSetsEqual`/`assertFieldMapsEqual` pattern: report BOTH "only in rule table" and "only in schema" on mismatch, not just a boolean).
  6. Assert: the schema's top-level `required` array is exactly `["name"]`.
  7. Write each assertion as its own `t.Run` subtest so a future schema update's failure mode is immediately legible (which invariant broke, not just "sync test failed").
- **Files**: `internal/pluginjson/validate_schema_sync_test.go` (new).
- **Parallel?**: Yes, relative to T010 (different file, no shared state) -- but both need T008's fixture and WP01's rule table to already exist.
- **Notes**: This test file necessarily reaches into WP01's unexported rule table -- that is intended and is why this file lives in `package pluginjson` (internal test), not `pluginjson_test`. If WP01's rule table type names differ slightly from this prompt's suggested names, adapt to what WP01 actually shipped; do not silently work around a real mismatch by loosening this test's assertions.

### Subtask T010 [P] -- validate_property_test.go

- **Purpose**: NFR-004's "zero false positives" claim needs a randomized witness, not just the fixed table-driven cases WP01 already wrote.
- **Steps**:
  1. Write a `testing/quick`-compatible generator (a type implementing `Generate(rand *rand.Rand, size int) reflect.Value`, or a manual loop calling `quick.Value`/your own random-object builder -- either is acceptable) that produces a JSON object using ONLY known field names (from the rule table, `Source` in `{schema, docs, apm-go}`) with values of the CORRECT `Kind` for each included field (a random subset of fields, random string/bool/array contents, but always type-correct and always syntactically valid as a path when `IsPath` is set -- e.g. always prefix generated path strings with `./`).
  2. Run at least 100 iterations (`quick.Config{MaxCount: 100}` or an explicit loop) marshaling each generated object to JSON, calling `Validate`, and asserting `len(report.Findings) == 0`.
  3. On a failure, `quick.Check`'s shrinking (if you use it) or your own loop should print the exact generated JSON that broke the invariant -- make failures reproducible, not just "test failed."
- **Files**: `internal/pluginjson/validate_property_test.go` (new).
- **Parallel?**: Yes, relative to T009.
- **Notes**: Do NOT generate unknown fields or wrong-typed values here -- that is the fuzz test's (T011) job. This property test's entire point is proving the validator never cries wolf on legitimate input; keep the generator strictly inside the "known and correctly-typed" envelope.

### Subtask T011 -- validate_fuzz_test.go FuzzValidateBytes

- **Purpose**: NFR-002's no-panic, no-memory-exhaustion guarantee, exercised against genuinely adversarial byte sequences, not just the hand-picked Structure test cases WP01 already has.
- **Steps**:
  1. Write `func FuzzValidateBytes(f *testing.F)` calling `Validate([]byte)` directly (not through the CLI) inside `f.Fuzz(func(t *testing.T, data []byte) { Validate(data) })` -- the only assertion needed is "does not panic and returns" (Go's native fuzzer already catches panics and hangs on its own).
  2. Seed the corpus (`f.Add([]byte(...))`) with one entry per spec.md US3 Structure scenario: `{` (unterminated), `[]` (valid JSON, wrong top-level shape), an empty byte slice, a byte slice containing `0xFF` (invalid UTF-8), a large deeply-nested `[[[[...` sequence (representative of the 1 MiB case -- the seed itself can be much smaller; the fuzzer will explore size on its own), and bytes sized just over 5 MiB (representative of the 6 MiB case -- again, seed a smaller marker input, since committing a literal 6 MiB fixture to git is unnecessary; the defensive length check in `Validate` triggers on any oversized input regardless of exact size).
  3. Also seed one valid, well-formed manifest (e.g. the same bytes as WP01's scaffold-based zero-finding test) and one manifest with a duplicate top-level key -- these exercise the NON-crash, NON-Structure-failure paths too, giving the fuzzer a foothold to mutate into every other check category.
  4. Do not add any assertion beyond "no panic" in the fuzz function body itself -- this is intentionally a crash-oracle-only fuzz test, not a correctness fuzz test (correctness is T007's and T010's job).
- **Files**: `internal/pluginjson/validate_fuzz_test.go` (new).
- **Parallel?**: No -- write and get this compiling before T012 (which runs it).
- **Notes**: Go's fuzzing corpus persists discovered failing inputs under `testdata/fuzz/FuzzValidateBytes/` automatically when `go test -fuzz` finds one -- if that happens during T012, do NOT delete the generated failure file; fix `Validate` (report the finding to WP01 if the bug is in WP01's owned file) and re-run until clean, then decide with the reviewer whether to commit the regression corpus entry.

## Risks & Mitigations

- Schema pattern-string matching (T009 step 3) is a plain substring/equality check on the `"pattern"` value, not a real regex-engine invocation -- if the vendored schema ever expresses the path constraint differently (e.g. a different anchor syntax), this test's detection breaks silently. Mitigate by asserting the schema's declared pattern value is exactly `"^\\./"` wherever you rely on it, failing loudly (not skipping) if it is not.
- A `testing/quick` generator that accidentally includes a field this WP considers "known" but the CLI/rule table does not yet support will produce false failures unrelated to the real invariant -- keep the generator's field list derived FROM the rule table at test time (read `rule.Name`/`rule.Kind` directly), never a second hand-maintained list that can drift from WP01's actual table.
- Committing a discovered fuzz failure's regression corpus file (`testdata/fuzz/...`) is fine and expected if T012 finds one; do not gate this WP's completion on avoiding that -- gate it on the bug being fixed and the corpus entry passing afterward.
