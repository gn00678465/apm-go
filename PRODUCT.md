## Platform

web

The web platform covers the documentation surface (confirmed 2026-08-29). The product's other confirmed surface is the CLI's own terminal UI (`internal/ux/`), which is not a web/native platform: any work there is governed by the terminal constraints in Operating Context, not by web design guidance.

## Users

- **AI-agent users / developers** (primary): run `apm-go init`, `install`, `compile`, `update`, `uninstall`, `audit` inside their own repositories to produce and maintain the root context files AI agents read on startup (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) and to manage package + MCP-server dependencies declared in `apm.yml` / `apm.lock.yaml`.
- **Marketplace / plugin authors** (primary): run `marketplace init`, `marketplace package add`, `marketplace audit`, `plugin init`, `pack` to author a marketplace, package skills/instructions, and publish Claude Code plugins (`marketplace.json`, `plugin.json`, `.mcp.json`).

Both audiences work in a terminal, frequently non-interactively (CI, agent-driven shells). Other audiences (platform / CI teams) exist in practice but were not confirmed as primary.

## Product Purpose

apm-go is an Agent Package Manager shipped as a single static Go binary with no interpreter or runtime dependency. It compiles `.apm/` primitives (instructions, agents, chat modes, memory) into agent context files, installs/uninstalls packages and MCP server configurations from marketplaces, and packages plugins for distribution.

Success: a user gets deterministic files, output, and exit codes from one binary installed via `install.sh` or a GitHub release, with no runtime to set up.

## Positioning

**Single static binary + a verified, extended command surface.** Output bytes, exit codes, and generated file trees are treated as a contract and gated in CI (`tools/parity`), so scripts and agents can depend on them. On that base apm-go ships its own additions — `pack --claude-source-style url`, `pack --json`, `--check-versions` / `--check-clean` release gates, top-level `doctor`, `normalize`, `validate`, `marketplace package update` — each documented at its site in `cmd/apm-go/*.go`. Upstream additions are ported on the same contract; `pack --strict-metadata`, the read-only `pack --check-clean`, and the Git URL rewrite safety check came from upstream 0.29.1.

## Operating Context

- Runs in a terminal; output goes through `internal/ux/`, which auto-detects TTY, `NO_COLOR`, and CI (`CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `BUILDKITE`, `TF_BUILD`, `JENKINS_URL`). Non-TTY/CI disables spinners and prompts; `NO_COLOR` disables color but **not** prompting.
- `ux.Error` / `ux.Warn` always land on stdout.
- Under CI, `install` defaults to frozen (lockfile-only) mode.
- A user's `apm.yml` is a hand-edited file; every mutation is a round-trip patch that preserves comments, ordering, and formatting. `apm.lock.yaml` is written whole in the Oracle's layout (issue #50): keys apm-go does not model survive, comments and the quote style of the old file do not.
- Git is a subprocess run under a hardened environment (no credential prompts, transport allow-list). On this project's development machine there is no SSH key, which is why `--claude-source-style url` exists for installable marketplaces.
- Distribution: `install.sh` (defaults to latest stable; pre-release tags are GitHub prereleases), GitHub Releases, mise (`github:gn00678465/apm-go`, through its `github` backend), `go build`. The release version is injected from the git tag at release build time (`internal/version/version.go`); local builds report `dev`.

### Terminal UI design

Presentation rules the CLI's own terminal output follows. Words, order, exit codes, and generated files are not presentation and are not covered here.

**Status symbols.** Every status line starts with one centered, colored, width-3 symbol from the single vocabulary in `internal/ux/colors.go`. Brackets are never printed, on any stream, interactive or piped.

| class | symbol |
|---|---|
| success | ` + ` |
| info | ` i ` |
| warning | ` ! ` |
| error | ` x ` |
| progress | ` > ` |
| list | ` * ` |
| plan diff update / remove / unchanged | ` ~ ` ` - ` ` = ` |

Call sites never choose a glyph; they call the `ux` printer for the class (`ux.Success`, `ux.Info`, `ux.Warn`, `ux.Error`, `ux.Progress`, `ux.List`). `ux.Plain` is for complete rows or text without a status symbol. Mixing symbol styles across commands was an earlier defect; one vocabulary is the fix.

**Interactive `init` / `plugin init`.** The interactive session is rendered as one clack-style transcript on stderr (`ux.NewClack`, `cmd/apm-go/init.go`): the prompts, an "About to create" note, a "Created project directory" progress line, and a single "Initializing" note that holds the success content (title, Created Files table, Next Steps, tips). Rules that must hold:

- the left frame border is continuous — no glyph or box line starts at column 0 inside the frame;
- status symbols inside the frame are the project symbols above;
- notes are capped to terminal width and wrap (`Clack.Note`), so a wide terminal or a long path never breaks the layout;
- consecutive steps keep a blank spacer line so a note does not sit directly against the previous prompt;
- the non-interactive path (`--yes`, non-TTY, CI) prints the same success content as plain status lines with the same symbols;
- `plugin init` shares the same core (`runInitCore`) and the same frame; it has its own flag set (`--verbose`, `--format`, `--claude-plugin`) and does not carry consumer init's `--force`;
- no docs/star footer is printed after the success block.

## Capabilities and Constraints

Command surface (`apm-go --help`): `audit`, `compile`, `completion`, `deps` (list/tree), `doctor`, `experimental`, `init`, `install`, `marketplace` (add/list/browse/update/remove/validate/init/package/audit), `normalize`, `pack`, `plugin` (init/validate), `search`, `self-update`, `uninstall`, `update`, `validate`.

Constraints future work must preserve:

- Output contract: words, exit codes, output bytes, and file trees are gated in CI. Only line-wrap, box-drawing, help layout, status-symbol shape (normalized by the runner), timestamps, and paths may be waived; every waiver is recorded with its reason. The gate runs against the latest stable upstream release of the Oracle, resolved when CI runs, so a new upstream release can turn the gate red with no change in this repository. An apm-go-only command that the Oracle does not have cannot have a corpus case; its contract is pinned instead by `tools/realexec.sh` at the same strength (full stdout, stderr, exit code, file tree) and recorded in a ticket that quotes the user ruling - ticket 34 covers `plugin validate`, ticket 37 covers `marketplace package update`, and the exemption never extends by analogy to another command.
- Exit codes: usage errors are 2; specific codes via `withExitCode()`. `pack` exits 3 for a failed `--check-versions`, 4 for a failed `--check-clean`, and 5 for a failed `--strict-metadata`; 5 is decided before any producer runs, and 3 wins over 4.
- JSON bytes from pack/scaffold go through `bundle.MarshalIndent` (2-space indent, non-ASCII escaped as `\uXXXX`); the marketplace builder alone emits UTF-8 unescaped.
- YAML ingestion is restricted to the OpenAPM safe subset (no anchors, merge keys, custom tags) — `spec/conformance/openapm-v0.1.md`.
- Marketplace metadata certification (`pack`): each resolved package has one metadata outcome (`fetched`, `empty`, `failed`, `offline`, `local`, `explicit`), reported in `pack --json` as `metadata_enrichment`. Only the Claude output uses package metadata. `--strict-metadata` fails with exit 5 before anything is written when a selected output's metadata could not be fetched. `--check-clean` is always read-only (it implies `--dry-run`), reuses the metadata of the same run, and reports an output whose metadata could not be fetched as `uncertifiable` (exit 4) without comparing it. An outcome's cause never carries raw error text, a URL, or a credential.
- Git URL rewrite safety: before every network git subprocess, apm-go reads the effective `url.*.insteadOf` rules and refuses a rewrite that downgrades the transport, adds credentials, or moves an authenticated remote to another host or origin; a config that cannot be read fails the operation instead of being skipped.
- Credential scanning (`internal/security/`) runs in `pack` (warn policy) and `audit` (report); its policy gate is fail-closed (unknown policy = block). It is not part of install/deploy.
- Deploy targets: claude, codex, copilot, antigravity, opencode, agent-skills (adapter per target).
- `devDependencies.mcp` (issue #97): the MCP servers `apm.yml` declares there are configured by `install`, `install --global`, a frozen install and `update` as those of `dependencies.mcp` are, with the same output, config files and lock records, as in Oracle 0.33.0. The servers of `dependencies.mcp` come first, and of two servers with one name the first declared is configured. A dependency's own `devDependencies.mcp` is not configured, as in the Oracle. Before issue #97 apm-go configured none of them and printed nothing about them.
- Codex MCP config: a server entry in `.codex/config.toml` has no `id` field, because Codex's config schema has no such field and `--strict-config` rejects the file over it. Deviation: the Oracle writes `id = ""` on stdio and http entries (upstream microsoft/apm#3087). A new `install` drops an old `id` from the entries apm-go manages; an entry for a server that is no longer in `apm.yml` is removed whole when the old lock records the server (see Stale MCP servers), and is not touched otherwise.
- MCP `enabled`: the value an `apm.yml` MCP entry declares for `enabled` is written to `opencode.json` as it is, whatever its type (`true` when the entry has none), and recorded in the lock's `mcp_configs`, for a self-defined and a registry server and whatever the targets. It is read as the Oracle's YAML 1.1 loader reads it: a plain `no`, `off` or `False` is `false`, a quoted one a string. The config files of the other targets do not carry it, as in the Oracle. A change of the type of `enabled` alone (`false` to `'false'`, `false` to `0`) is a change: the lock is written again and `install` prints the server as updated. No other field of a server is compared by type, so an Oracle lock that records an integer in `args` or `env` stays as it is. Deviation: the Oracle compares `false` and `0` as equal and keeps its old lock.
- Stale MCP servers (issue #71): `install`, `install --global` and `update` remove from the MCP config files a server that the old `apm.lock.yaml` records and that is no longer declared or no longer goes to a target, before the lock is written, as Oracle 0.33.0 does. A server is declared when `apm.yml` names it under `dependencies.mcp` or `devDependencies.mcp`, or a direct dependency's own `apm.yml` names it under `dependencies.mcp`; a server only a transitive dependency declares is not, since `install` never deploys one. A declared server stays whatever becomes of it in the run: a registry that cannot be reached or does not have it, a placeholder that is refused, a target that skips it or fails to write its file. Each of these is the warning it was, and the lock does not record the server, as before. When MCP servers are declared, a target that is no longer active (a `targets:` in `apm.yml` or a `--target` that no longer names it) loses every server the old `mcp_target_servers` lists for it, then every active target loses each server of the old `mcp_servers` that is no longer declared. When none is declared, every target the old `mcp_target_servers` lists, an active one included, loses its listed servers that the old `mcp_servers` has. A lock with `mcp_servers` and no `mcp_target_servers` (apm-go v0.3.0) gives the first rule nothing, as the Oracle's legacy adoption does for a lock with no `mcp_configs`. The file is the one `install` writes, below the project or, for `--global`, `HOME`. Other servers and keys of the file stay, and the file is written the way `install` writes it, so in a JSON file other than `.mcp.json` the keys come out sorted and `.codex/config.toml` is rendered again; a file that has none of the names is not written. Each removed server prints `Removed stale MCP server '<name>' from <label>` (`.mcp.json`, `Codex CLI config`, `Copilot CLI config`, `Antigravity MCP config`, `opencode.json`; a success line for codex and copilot, an info line for the others) after the MCP block, or after the package blocks when there is no MCP block, and before the last line: first the targets that are no longer active, then the active ones, each set by target name, and the names of one file sorted, where the Oracle's order changes from run to run. `update` prints them before its summary. The last line does not change: an install whose only change is these servers ends with `No changes -- ...`, as in the Oracle. A file that cannot be read, parsed or written ends the command with exit 1 and `MCP cleanup failed for <label>: <reason>. Check the config path and permissions, then retry.`, the reason being apm-go's own text; a file, or a directory between the deploy root and it, that is a symlink ends it with exit 1 and `Refusing to clean symlinked MCP config: <label> (<absolute path>). Replace the symlink with a regular file or directory, then retry.`, and nothing is read through it. The lock is not written in either case. Only a target with a name to remove is looked at. `install --mcp`, `uninstall` and a frozen install do not do this cleanup; the Oracle's `install --mcp` does not either. Deviations: the Oracle cleans `.mcp.json` only when `.claude/` is a directory and `opencode.json` only when `.opencode/` is one, and apm-go cleans both whatever the directories, because it writes `opencode.json` without making `.opencode/`; a name with a `/` is removed as written and not also by the part after the last `/`, because apm-go keys every entry by the full name; copilot's file is `.github/mcp-config.json` and the `--global` files are apm-go's own; a recorded target that is not one of apm-go's MCP targets (claude, codex, copilot, antigravity, opencode), such as the Oracle's `cursor`, is skipped; a frozen install cleans nothing, because it writes no lock; the Oracle keeps the key order of a JSON file it cleans.
- Packages no longer in `apm.yml` (issue #75): `install`, `install --global` and `update`, with no package named, remove the files that a package the old `apm.lock.yaml` records, and that the run no longer resolves (a dependency taken out of `apm.yml`, or a transitive one its parent no longer declares), deployed, as Oracle 0.33.0 does. A file is removed only when it has the hash the lock records, and a path the run deploys for another package, an MCP config file and a directory a `--global` deploy left to the user are not touched. The paths are judged against every target apm-go deploys to, not only this run's, so after `--target claude,copilot` and then `--target claude` the package's `.github/` and `.agents/skills/` files go too, as in the Oracle. The command prints ` i Cleaned <N> file(s) from packages no longer in apm.yml` (a skill's directory counts as one), then each removed path, before the lines of the stale files of the packages that stay. A file with another hash, or one that cannot be removed, stays with a warning, and the lock keeps the package's entry with only those files and their old hashes; a package with no such file leaves the lock. `install <pkg>` and `update <pkg>` remove nothing and keep the package's whole entry in the lock, as the Oracle does when it is given packages. `apm_modules/<key>` stays, as in the Oracle. A lock in the format before issue #50 records a local package as `_local/<name>-<8 hex>`: when `apm.yml` still declares that package, the entry is the package's old record, so the files the package no longer deploys are removed as stale files and the lock records the package under `_local/<name>` alone; when `apm.yml` no longer declares it, it is removed as above, and a file that stays is kept under the old key (both measured to give the files and lock of Oracle 0.33.0). A recorded file that the run does not deploy keeps its record and old hash unless it is known to be gone: a file that cannot be read, for example below a directory of mode 000, may still be on disk and stays in the lock, for a package no longer declared and for one that stays; a file the user deleted leaves the lock. In that case the command warns and exits 0. Deviations: apm-go lists the removed paths, as it does for stale files (issue #30); a path under no apm-go target, such as the Oracle's `.cursor/`, is not removed and leaves the lock, where the Oracle removes a file of each target it knows; the warning is apm-go's own text (` ! keeping "<path>": modified since deploy (hash mismatch)`), not the Oracle's `Kept user-edited file ...` and `Skipped removing ...` lines; the last line has no `(<N> stale files cleaned)`, as for stale files (ticket 32 item 24); a file that cannot be read or removed is a warning with exit 0, where Oracle 0.33.0 ends with exit 1, because apm-go's stale-file cleanup warns and goes on; for an old-format entry of a package still declared, apm-go reports the removed files as that package's stale files, where the Oracle reports them as files of a package no longer in `apm.yml`.
- A dependency's `targets:` (issue #69): an object-form entry in `apm.yml` (`path:`, `git:` and the registry `id:` form; not `git: parent`, which is refused with the Oracle's `Unsupported field(s) for parent git dependency: 'targets'`) may carry `targets:`, and the package then deploys only to the active targets the list names, as in Oracle 0.33.0. This holds for a direct dependency and for a dependency a package's own `apm.yml` declares (measured for a direct local, git and registry dependency, for a git dependency a git package declares, a registry dependency a registry package declares, and a git or registry dependency a local package declares), and for `install`, `install --global`, a frozen install, `update` and the hand-over of `uninstall`; `update` prints no warning for a package it skips. When two packages have a primitive of the same name, each target is given to the first package that allows that target, so one package can own the Claude file and another the Copilot file. A skill directory that several targets write (`.agents/skills/<name>`, for copilot, codex, opencode and agent-skills) is one package's: the first package that one of those targets deploys the skill from, as in the Oracle; the lock records it under that package with the bytes on disk. The list is read as the Oracle reads it, with its reason texts and exit 1 before any file is written: `null` is no list; a value that is not a list is `'targets' field must be a list of target names`; an empty list is `targets: must contain at least one target; remove the field to route primitives to all active install targets.`; an entry that is not a non-empty string is `Each entry in 'targets' must be a non-empty string`; an entry, trimmed and lowercased, has to be one of the Oracle's 16 target names (`agent-skills, antigravity, claude, codex, copilot, copilot-app, copilot-cowork, cursor, gemini, grok-build, grok-cloud, hermes, kiro, openclaw, opencode, windsurf`), else `Unknown target '<name>'. Valid targets: <the 16 names>.`, with ` Did you mean '<name>'?` for a name within edit distance 2; an alias (`vscode`) and `all` are refused. The text before the reason is apm-go's own (`validate apm.yml: dependency entry <N>: ...`). A package whose list names no active target deploys nothing, its install block is its header alone, and before the last line `install` prints ` ! [<name>] Per-dependency targets [<list>] do not overlap active install targets; skipping` (`<name>` is the declared path of a local package, `owner/repo` for github.com and for a registry package's `id`, `<host>/owner/repo` for another host); it is still counted and recorded. The lock records the list, deduplicated and sorted, as `target_subset`, and a change of the list alone writes the lock again; files of a target the list no longer allows are cleaned as stale. MCP servers a package declares are configured for every active target whatever its `targets:`, and `compile` is not affected, as in the Oracle. `install --target` does not write `targets:` into `apm.yml`, as in the Oracle.
- `plugin validate` has no upstream Oracle equivalent (apm-go-only, closing the second half of issue #13); its output contract is fixed by `tools/realexec.sh`, not a `tools/parity` corpus case.
- `marketplace package update` has no upstream Oracle equivalent (apm-go-only, issue #25): it writes the upgrade `marketplace outdated` reports for a SHA-pinned package back to the authoring config, replacing only the `version` and `ref` values. A SHA pin with no version that has a `subdir` moves only when the content of that directory (its git object id) at the default-branch tip differs from the pinned commit; with the same content nothing is written, and `marketplace outdated` reports the entry as up to date (issue #39). Its output contract is fixed by `tools/realexec.sh` (ticket 37), not a `tools/parity` corpus case; the steps there are network-free, so the path that writes is covered by `go test` with a canned `RefLister` and a canned `SubdirObjectReader`.
- Lockfile (`apm.lock.yaml`): the layout is the Oracle's (field order, quoting, list indentation, a `deployments` section, no `generated_at`); the file has mode `0600`. MCP servers are recorded in it as `mcp_servers`, `mcp_configs` and `mcp_target_servers`, by `install` and by `install --mcp`; an MCP config file such as `.mcp.json` is not listed as a deployed file. A deployed skill's directory (`<target root>/skills/<name>`) is listed in `deployed_files` and `deployments` with no content hash, as the Oracle lists it, by a project install and by `install --global`. A git dependency whose root is a skill (a root `SKILL.md`) deploys the skill without the `.git` of the package root, and the lock records no path below it, as in Oracle 0.33.0, which drops that `.git` when it clones the package into `apm_modules/`; a `.git` deeper in the skill is deployed, and a local-path package keeps its `.git`, as in the Oracle (issue #113). A registry package keeps the `.git` its archive holds, deployed and recorded, as the Oracle extracts the whole archive; a frozen install and the `uninstall` hand-over, which read a transitive dependency's source from the lock, do the same. When a lock written before issue #113 records such paths, a project `install` removes, as stale files, the ones that still have the recorded hash, and keeps one with another hash, with its warning and its record; `install --global` drops the records and removes nothing, because the files are the `.git` of the checkout in `apm_modules/`. Deviation: through the `--global` skill symlink the `.git` is still there to see, where the Oracle copies the skill. The keys of an MCP server's `env` and `headers` keep the order they were declared in, in the lock, in `apm.yml` and in the Claude `.mcp.json`. Whether the lock has an `apm_version` line follows the command and the flag, also for a lock that already exists and changes in nothing else: `install` and `install --mcp` write it for a lock that records a dependency or an MCP server, `--no-provenance` leaves it out, and a lock of the project's own content alone keeps the line it had. The value of an existing line is not a reason to write the lock again; when a lock is written, is to have the line, and the value of its line is empty, the line is written with the current version. `install --mcp` applies this also when it ends without recording anything (a registry entry that does not change, a server that no target takes): an existing lock whose line has to come or go is then written whole, like every other lock, and one that already agrees is not touched. The lock has the line when the document has a top-level `apm_version` key, whatever its value or quoting. A user who declines to replace an entry changes no file. Deviation: the Oracle has no such flag and does not add a missing line. A lock in the format before issue #50 is read without error: a frozen install uses it as it is, every other install, and `update`, writes it again in the current format and removes the `apm_modules/` directory the old lock named. A dependency that is a directory of a repository (an entry with a `virtual_path` that is a directory) records as `resolved_commit` the commit of the repository it was taken from, whether or not the project is itself in a git repository, and a frozen install fetches that commit. Such an entry has no `tree_sha256`, as in the Oracle's lock: its content is pinned by the commit and by `deployed_file_hashes`. Deviation from the project's own spec: `req-lk-015` asks for a `tree_sha256` on every git source. A lock written before issue #65 for a project inside a git repository records the project's own commit for such an entry, with a `tree_sha256`; a frozen install of it fails at the download, and an `install` that is not frozen writes the right commit. A git dependency's entry records `version` as Oracle 0.33.0 does (issue #82): the version a semver constraint resolved to (tag `v1.2.3` is `1.2.3`); else, for a package with an `apm.yml` that has `.apm/` or declares dependencies, that file's `version`; for a Claude plugin (`.claude-plugin/` or a `plugin.json`, with no such `apm.yml`), the `version` of `plugin.json`, else of `apm.yml`, and the commit's first seven characters when that is `0.0.0` or missing; for another package with an `apm.yml`, its `version`; and `unknown` for the rest (a root `SKILL.md`, a skill bundle, a directory of a repository with no `apm.yml`). Each was measured against the Oracle's lock. A hook package with no `apm.yml` is recorded as `unknown`; Oracle 0.33.0 refuses to install one (`Downloaded package has no apm.yml or SKILL.md`), so it has no value to match. A lock written before issue #82 lacks these `version` lines, so the next `install` or `update` writes it again once, with the same terminal text as an install that changes nothing. The other fields of a git entry the Oracle writes (`name`, `package_type`, `is_virtual`) are not written (#88), and the fields of a registry entry were ported from the Oracle's source and have not been measured against it. `deployed_file_hashes` and `local_deployed_file_hashes` hold the hash defined under Frozen install, with CRLF read as LF (issue #119). A lock that recorded the hash of a file's CRLF bytes, as apm-go v0.4.0 did on Windows under git's `core.autocrlf=true` and on any system for a source with CRLF, is written again once by the next `install` or `update` that is not frozen. A lock that differs from what apm-go writes in its line endings alone, as git checks a committed lock out with CRLF under `core.autocrlf=true`, is not written again, as the Oracle writes the lock only when its state changed. Stale cleanup, the cleanup of packages no longer in `apm.yml`, `uninstall` and its hand-over take a file as the one deployed when its normalized hash or the hash of its raw bytes is the recorded one, so after the upgrade such a file is removed or handed over, and not kept as edited since deploy. This is apm-go's own: the Oracle never recorded a raw hash and compares the normalized one alone (`integration/cleanup.py:448-470`).
- A missing `apm.yml` (issue #81): `install <pkg>` and `install -g <pkg>`, when not frozen, create it before they validate the packages, as Oracle 0.33.0 does. Its `name` is the name of the directory (for `-g`, of `HOME`), or `my-project` when that name is empty, blank, holds a `/` or `\`, or is `..`; then `version: 1.0.0`, `description: APM project for <name>`, `author` from `git config user.name` (`Developer` when there is none), the Oracle's comments, `dependencies`, `includes: auto` and `scripts: {}`. A `--target` value goes into `targets:` as the Oracle maps it: each token, `vscode` and `agents` as `copilot`, `all` as `claude, codex, copilot, cursor, gemini, grok-build, kiro, opencode, windsurf`, a name outside the Oracle's manifest list (`agy`, `x-<vendor>-<name>`) left out, without duplicates, sorted; with nothing to write the file has the Oracle's commented skeleton. Before ` + Validating ...` the command prints ` + Created apm.yml` (for `-g`, the absolute path of `~/.apm/apm.yml`) and, when it wrote targets, ` i Targets set: <targets> (persisted to <the same path>)`; the packages are written into the file also when `apm.lock.yaml` does not change. When the run then fails, wherever it fails, the file is removed and ` i Removed apm.yml created by the failed install.` comes before the error, with the exit code the failure has; a file that cannot be removed gives the warning ` ! Failed to remove apm.yml created by this install. Delete apm.yml manually before retrying.` An `apm.yml` that exists is not given a `targets:`, and one it has is not changed. `install -g --mcp` with no `~/.apm/apm.yml` creates it with the same fields and no comments, `targets:` being the targets the install configures, in the order of `--target`, without duplicates, with `all` expanded and a target that has no MCP config left out (`claude,agent-skills` is `claude`, `agy` is `antigravity`, as in the Oracle), and no `targets:` key without `--target`; it prints ` + Created <path>` before the MCP block. ## Product Principles

1. **Output is a contract.** Words, bytes, exit codes, and file trees are gated in CI; an unrecorded difference is a bug until a waiver names it.
2. **Additions are opt-in supersets.** New flags and commands default to the existing behavior and are documented at their site in code.
3. **One vocabulary on every stream.** Status symbols, framing, and wording are the same in interactive, piped, and CI output; the ux layer, not call sites, decides presentation.
4. **User files are sacred.** `apm.yml` and context files are patched, never rewritten. The lockfile is machine-written in one layout, the Oracle's, and keeps every key it does not model.
5. **Fail closed.** Unknown security policy blocks; unknown waiver IDs fail the gate; unsafe YAML is rejected.

## Accessibility & Inclusion

- Terminal output must remain meaningful without color (`NO_COLOR`) and without a TTY (CI, pipes); status is carried by the symbol glyph, not color alone.
- Documentation is bilingual (English / Traditional Chinese) — the docs surface should preserve both.
