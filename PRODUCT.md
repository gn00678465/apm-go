# Product

## Platform

web

The web platform covers the documentation surface (confirmed 2026-08-29). The product's other confirmed surface is the CLI's own terminal UI (`internal/ux/`), which is not a web/native platform: any work there is governed by the terminal constraints in Operating Context, not by web design guidance.

## Users

- **AI-agent users / developers** (primary): run `apm-go init`, `install`, `compile`, `update`, `uninstall`, `audit` inside their own repositories to produce and maintain the root context files AI agents read on startup (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) and to manage package + MCP-server dependencies declared in `apm.yml` / `apm.lock.yaml`.
- **Marketplace / plugin authors** (primary): run `marketplace init`, `marketplace package add`, `marketplace audit`, `plugin init`, `pack` to author a marketplace, package skills/instructions, and publish Claude Code plugins (`marketplace.json`, `plugin.json`, `.mcp.json`).

Both audiences work in a terminal, frequently non-interactively (CI, agent-driven shells). Other audiences (platform / CI teams) exist in practice but were not confirmed as primary.

## Product Purpose

apm-go is an Agent Package Manager shipped as a single static Go binary with no interpreter or runtime dependency. It compiles `.apm/` primitives (instructions, agents, chat modes, memory) into agent context files, installs/uninstalls packages and MCP server configurations from marketplaces, and packages plugins for distribution.

Success: a user gets deterministic files, output, and exit codes from one binary installed via `install.sh` or a GitHub release, with no runtime to set up.

## Positioning

**Single static binary + a verified, extended command surface.** Output bytes, exit codes, and generated file trees are treated as a contract and gated in CI (`tools/parity`), so scripts and agents can depend on them. On that base apm-go ships its own additions — `pack --claude-source-style url`, `pack --json`, `--check-versions` / `--check-clean` release gates, top-level `doctor`, `normalize`, `validate`, `marketplace package update` — each documented at its site in `cmd/apm-go/*.go`. Upstream additions are ported on the same contract; `pack --strict-metadata`, the read-only `pack --check-clean`, and the Git URL rewrite safety check came from upstream 0.29.1.

## Operating Context

- Runs in a terminal; output goes through `internal/ux/`, which auto-detects TTY, `NO_COLOR`, and CI (`CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `BUILDKITE`, `TF_BUILD`, `JENKINS_URL`). Non-TTY/CI disables spinners and prompts; `NO_COLOR` disables color but **not** prompting.
- `ux.Error` / `ux.Warn` always land on stdout.
- Under CI, `install` defaults to frozen (lockfile-only) mode.
- A user's `apm.yml` is a hand-edited file; every mutation is a round-trip patch that preserves comments, ordering, and formatting. `apm.lock.yaml` is written whole in the Oracle's layout (issue #50): keys apm-go does not model survive, comments and the quote style of the old file do not.
- Git is a subprocess run under a hardened environment (no credential prompts, transport allow-list). On this project's development machine there is no SSH key, which is why `--claude-source-style url` exists for installable marketplaces.
- Distribution: `install.sh` (defaults to latest stable; pre-release tags are GitHub prereleases), GitHub Releases, mise (`github:gn00678465/apm-go`, through its `github` backend), `go build`. The release version is injected from the git tag at release build time (`internal/version/version.go`); local builds report `dev`.

### Terminal UI design

Presentation rules the CLI's own terminal output follows. Words, order, exit codes, and generated files are not presentation and are not covered here.

**Status symbols.** Every status line starts with one centered, colored, width-3 symbol from the single vocabulary in `internal/ux/colors.go`. Brackets are never printed, on any stream, interactive or piped.

| class | symbol |
|---|---|
| success | ` + ` |
| info | ` i ` |
| warning | ` ! ` |
| error | ` x ` |
| progress | ` > ` |
| list | ` * ` |
| plan diff update / remove / unchanged | ` ~ ` ` - ` ` = ` |

Call sites never choose a glyph; they call the `ux` printer for the class (`ux.Success`, `ux.Info`, `ux.Warn`, `ux.Error`, `ux.Progress`, `ux.List`). `ux.Plain` is for complete rows or text without a status symbol. Mixing symbol styles across commands was an earlier defect; one vocabulary is the fix.

**Interactive `init` / `plugin init`.** The interactive session is rendered as one clack-style transcript on stderr (`ux.NewClack`, `cmd/apm-go/init.go`): the prompts, an "About to create" note, a "Created project directory" progress line, and a single "Initializing" note that holds the success content (title, Created Files table, Next Steps, tips). Rules that must hold:

- the left frame border is continuous — no glyph or box line starts at column 0 inside the frame;
- status symbols inside the frame are the project symbols above;
- notes are capped to terminal width and wrap (`Clack.Note`), so a wide terminal or a long path never breaks the layout;
- consecutive steps keep a blank spacer line so a note does not sit directly against the previous prompt;
- the non-interactive path (`--yes`, non-TTY, CI) prints the same success content as plain status lines with the same symbols;
- `plugin init` shares the same core (`runInitCore`) and the same frame; it has its own flag set (`--verbose`, `--format`, `--claude-plugin`) and does not carry consumer init's `--force`;
- no docs/star footer is printed after the success block.

## Capabilities and Constraints

Command surface (`apm-go --help`): `audit`, `compile`, `completion`, `doctor`, `experimental`, `init`, `install`, `marketplace` (add/list/browse/update/remove/validate/init/package/audit), `normalize`, `pack`, `plugin` (init/validate), `search`, `self-update`, `uninstall`, `update`, `validate`.

Constraints future work must preserve:

- Output contract: words, exit codes, output bytes, and file trees are gated in CI. Only line-wrap, box-drawing, help layout, status-symbol shape (normalized by the runner), timestamps, and paths may be waived; every waiver is recorded with its reason. The gate runs against the latest stable upstream release of the Oracle, resolved when CI runs, so a new upstream release can turn the gate red with no change in this repository. An apm-go-only command that the Oracle does not have cannot have a corpus case; its contract is pinned instead by `tools/realexec.sh` at the same strength (full stdout, stderr, exit code, file tree) and recorded in a ticket that quotes the user ruling - ticket 34 covers `plugin validate`, ticket 37 covers `marketplace package update`, and the exemption never extends by analogy to another command.
- Exit codes: usage errors are 2; specific codes via `withExitCode()`. `pack` exits 3 for a failed `--check-versions`, 4 for a failed `--check-clean`, and 5 for a failed `--strict-metadata`; 5 is decided before any producer runs, and 3 wins over 4.
- JSON bytes from pack/scaffold go through `bundle.MarshalIndent` (2-space indent, non-ASCII escaped as `\uXXXX`); the marketplace builder alone emits UTF-8 unescaped.
- YAML ingestion is restricted to the OpenAPM safe subset (no anchors, merge keys, custom tags) — `spec/conformance/openapm-v0.1.md`.
- Marketplace metadata certification (`pack`): each resolved package has one metadata outcome (`fetched`, `empty`, `failed`, `offline`, `local`, `explicit`), reported in `pack --json` as `metadata_enrichment`. Only the Claude output uses package metadata. `--strict-metadata` fails with exit 5 before anything is written when a selected output's metadata could not be fetched. `--check-clean` is always read-only (it implies `--dry-run`), reuses the metadata of the same run, and reports an output whose metadata could not be fetched as `uncertifiable` (exit 4) without comparing it. An outcome's cause never carries raw error text, a URL, or a credential.
- Git URL rewrite safety: before every network git subprocess, apm-go reads the effective `url.*.insteadOf` rules and refuses a rewrite that downgrades the transport, adds credentials, or moves an authenticated remote to another host or origin; a config that cannot be read fails the operation instead of being skipped.
- Credential scanning (`internal/security/`) runs in `pack` (warn policy) and `audit` (report); its policy gate is fail-closed (unknown policy = block). It is not part of install/deploy.
- Deploy targets: claude, codex, copilot, antigravity, opencode, agent-skills (adapter per target).
- Codex MCP config: a server entry in `.codex/config.toml` has no `id` field, because Codex's config schema has no such field and `--strict-config` rejects the file over it. Deviation: the Oracle writes `id = ""` on stdio and http entries (upstream microsoft/apm#3087). A new `install` drops an old `id` from the entries apm-go manages; an entry for a server that is no longer in `apm.yml` is removed whole when the old lock records the server (see Stale MCP servers), and is not touched otherwise.
- MCP `enabled`: the value an `apm.yml` MCP entry declares for `enabled` is written to `opencode.json` as it is, whatever its type (`true` when the entry has none), and recorded in the lock's `mcp_configs`, for a self-defined and a registry server and whatever the targets. It is read as the Oracle's YAML 1.1 loader reads it: a plain `no`, `off` or `False` is `false`, a quoted one a string. The config files of the other targets do not carry it, as in the Oracle. A change of the type of `enabled` alone (`false` to `'false'`, `false` to `0`) is a change: the lock is written again and `install` prints the server as updated. No other field of a server is compared by type, so an Oracle lock that records an integer in `args` or `env` stays as it is. Deviation: the Oracle compares `false` and `0` as equal and keeps its old lock.
- Stale MCP servers (issue #71): `install`, `install --global` and `update` remove from the MCP config files a server that the old `apm.lock.yaml` records and that is no longer declared or no longer goes to a target, before the lock is written, as Oracle 0.33.0 does. A server is declared when `apm.yml` names it under `dependencies.mcp` or `devDependencies.mcp` (apm-go does not deploy the latter, issue #97), or a direct dependency's own `apm.yml` names it under `dependencies.mcp`; a server only a transitive dependency declares is not, since `install` never deploys one. A declared server stays whatever becomes of it in the run: a registry that cannot be reached or does not have it, a placeholder that is refused, a target that skips it or fails to write its file. Each of these is the warning it was, and the lock does not record the server, as before. When MCP servers are declared, a target that is no longer active (a `targets:` in `apm.yml` or a `--target` that no longer names it) loses every server the old `mcp_target_servers` lists for it, then every active target loses each server of the old `mcp_servers` that is no longer declared. When none is declared, every target the old `mcp_target_servers` lists, an active one included, loses its listed servers that the old `mcp_servers` has. A lock with `mcp_servers` and no `mcp_target_servers` (apm-go v0.3.0) gives the first rule nothing, as the Oracle's legacy adoption does for a lock with no `mcp_configs`. The file is the one `install` writes, below the project or, for `--global`, `HOME`. Other servers and keys of the file stay, and the file is written the way `install` writes it, so in a JSON file other than `.mcp.json` the keys come out sorted and `.codex/config.toml` is rendered again; a file that has none of the names is not written. Each removed server prints `Removed stale MCP server '<name>' from <label>` (`.mcp.json`, `Codex CLI config`, `Copilot CLI config`, `Antigravity MCP config`, `opencode.json`; a success line for codex and copilot, an info line for the others) after the MCP block, or after the package blocks when there is no MCP block, and before the last line: first the targets that are no longer active, then the active ones, each set by target name, and the names of one file sorted, where the Oracle's order changes from run to run. `update` prints them before its summary. The last line does not change: an install whose only change is these servers ends with `No changes -- ...`, as in the Oracle. A file that cannot be read, parsed or written ends the command with exit 1 and `MCP cleanup failed for <label>: <reason>. Check the config path and permissions, then retry.`, the reason being apm-go's own text; a file, or a directory between the deploy root and it, that is a symlink ends it with exit 1 and `Refusing to clean symlinked MCP config: <label> (<absolute path>). Replace the symlink with a regular file or directory, then retry.`, and nothing is read through it. The lock is not written in either case. Only a target with a name to remove is looked at. `install --mcp`, `uninstall` and a frozen install do not do this cleanup; the Oracle's `install --mcp` does not either. Deviations: the Oracle cleans `.mcp.json` only when `.claude/` is a directory and `opencode.json` only when `.opencode/` is one, and apm-go cleans both whatever the directories, because it writes `opencode.json` without making `.opencode/`; a name with a `/` is removed as written and not also by the part after the last `/`, because apm-go keys every entry by the full name; copilot's file is `.github/mcp-config.json` and the `--global` files are apm-go's own; a recorded target that is not one of apm-go's MCP targets (claude, codex, copilot, antigravity, opencode), such as the Oracle's `cursor`, is skipped; a frozen install cleans nothing, because it writes no lock; the Oracle keeps the key order of a JSON file it cleans.
- Packages no longer in `apm.yml` (issue #75): `install`, `install --global` and `update`, with no package named, remove the files that a package the old `apm.lock.yaml` records, and that the run no longer resolves (a dependency taken out of `apm.yml`, or a transitive one its parent no longer declares), deployed, as Oracle 0.33.0 does. A file is removed only when it has the hash the lock records, and a path the run deploys for another package, an MCP config file and a directory a `--global` deploy left to the user are not touched. The paths are judged against every target apm-go deploys to, not only this run's, so after `--target claude,copilot` and then `--target claude` the package's `.github/` and `.agents/skills/` files go too, as in the Oracle. The command prints ` i Cleaned <N> file(s) from packages no longer in apm.yml` (a skill's directory counts as one), then each removed path, before the lines of the stale files of the packages that stay. A file with another hash, or one that cannot be removed, stays with a warning, and the lock keeps the package's entry with only those files and their old hashes; a package with no such file leaves the lock. `install <pkg>` and `update <pkg>` remove nothing and keep the package's whole entry in the lock, as the Oracle does when it is given packages. `apm_modules/<key>` stays, as in the Oracle. A lock in the format before issue #50 records a local package as `_local/<name>-<8 hex>`: when `apm.yml` still declares that package, the entry is the package's old record, so the files the package no longer deploys are removed as stale files and the lock records the package under `_local/<name>` alone; when `apm.yml` no longer declares it, it is removed as above, and a file that stays is kept under the old key (both measured to give the files and lock of Oracle 0.33.0). A recorded file that the run does not deploy keeps its record and old hash unless it is known to be gone: a file that cannot be read, for example below a directory of mode 000, may still be on disk and stays in the lock, for a package no longer declared and for one that stays; a file the user deleted leaves the lock. In that case the command warns and exits 0. Deviations: apm-go lists the removed paths, as it does for stale files (issue #30); a path under no apm-go target, such as the Oracle's `.cursor/`, is not removed and leaves the lock, where the Oracle removes a file of each target it knows; the warning is apm-go's own text (` ! keeping "<path>": modified since deploy (hash mismatch)`), not the Oracle's `Kept user-edited file ...` and `Skipped removing ...` lines; the last line has no `(<N> stale files cleaned)`, as for stale files (ticket 32 item 24); a file that cannot be read or removed is a warning with exit 0, where Oracle 0.33.0 ends with exit 1, because apm-go's stale-file cleanup warns and goes on; for an old-format entry of a package still declared, apm-go reports the removed files as that package's stale files, where the Oracle reports them as files of a package no longer in `apm.yml`.
- A dependency's `targets:` (issue #69): an object-form entry in `apm.yml` (`path:`, `git:` and the registry `id:` form; not `git: parent`, which is refused with the Oracle's `Unsupported field(s) for parent git dependency: 'targets'`) may carry `targets:`, and the package then deploys only to the active targets the list names, as in Oracle 0.33.0. This holds for a direct dependency and for a dependency a package's own `apm.yml` declares (measured for a direct local, git and registry dependency, for a git dependency a git package declares, a registry dependency a registry package declares, and a git or registry dependency a local package declares), and for `install`, `install --global`, a frozen install, `update` and the hand-over of `uninstall`; `update` prints no warning for a package it skips. When two packages have a primitive of the same name, each target is given to the first package that allows that target, so one package can own the Claude file and another the Copilot file. A skill directory that several targets write (`.agents/skills/<name>`, for copilot, codex, opencode and agent-skills) is one package's: the first package that one of those targets deploys the skill from, as in the Oracle; the lock records it under that package with the bytes on disk. The list is read as the Oracle reads it, with its reason texts and exit 1 before any file is written: `null` is no list; a value that is not a list is `'targets' field must be a list of target names`; an empty list is `targets: must contain at least one target; remove the field to route primitives to all active install targets.`; an entry that is not a non-empty string is `Each entry in 'targets' must be a non-empty string`; an entry, trimmed and lowercased, has to be one of the Oracle's 16 target names (`agent-skills, antigravity, claude, codex, copilot, copilot-app, copilot-cowork, cursor, gemini, grok-build, grok-cloud, hermes, kiro, openclaw, opencode, windsurf`), else `Unknown target '<name>'. Valid targets: <the 16 names>.`, with ` Did you mean '<name>'?` for a name within edit distance 2; an alias (`vscode`) and `all` are refused. The text before the reason is apm-go's own (`validate apm.yml: dependency entry <N>: ...`). A package whose list names no active target deploys nothing, its install block is its header alone, and before the last line `install` prints ` ! [<name>] Per-dependency targets [<list>] do not overlap active install targets; skipping` (`<name>` is the declared path of a local package, `owner/repo` for github.com and for a registry package's `id`, `<host>/owner/repo` for another host); it is still counted and recorded. The lock records the list, deduplicated and sorted, as `target_subset`, and a change of the list alone writes the lock again; files of a target the list no longer allows are cleaned as stale. MCP servers a package declares are configured for every active target whatever its `targets:`, and `compile` is not affected, as in the Oracle. `install --target` does not write `targets:` into `apm.yml`, as in the Oracle.
- `plugin validate` has no upstream Oracle equivalent (apm-go-only, closing the second half of issue #13); its output contract is fixed by `tools/realexec.sh`, not a `tools/parity` corpus case.
- `marketplace package update` has no upstream Oracle equivalent (apm-go-only, issue #25): it writes the upgrade `marketplace outdated` reports for a SHA-pinned package back to the authoring config, replacing only the `version` and `ref` values. A SHA pin with no version that has a `subdir` moves only when the content of that directory (its git object id) at the default-branch tip differs from the pinned commit; with the same content nothing is written, and `marketplace outdated` reports the entry as up to date (issue #39). Its output contract is fixed by `tools/realexec.sh` (ticket 37), not a `tools/parity` corpus case; the steps there are network-free, so the path that writes is covered by `go test` with a canned `RefLister` and a canned `SubdirObjectReader`.
- Lockfile (`apm.lock.yaml`): the layout is the Oracle's (field order, quoting, list indentation, a `deployments` section, no `generated_at`); the file has mode `0600`. MCP servers are recorded in it as `mcp_servers`, `mcp_configs` and `mcp_target_servers`, by `install` and by `install --mcp`; an MCP config file such as `.mcp.json` is not listed as a deployed file. A deployed skill's directory (`<target root>/skills/<name>`) is listed in `deployed_files` and `deployments` with no content hash, as the Oracle lists it, by a project install and by `install --global`. The keys of an MCP server's `env` and `headers` keep the order they were declared in, in the lock, in `apm.yml` and in the Claude `.mcp.json`. Whether the lock has an `apm_version` line follows the command and the flag, also for a lock that already exists and changes in nothing else: `install` and `install --mcp` write it for a lock that records a dependency or an MCP server, `--no-provenance` leaves it out, and a lock of the project's own content alone keeps the line it had. The value of an existing line is not a reason to write the lock again; when a lock is written, is to have the line, and the value of its line is empty, the line is written with the current version. `install --mcp` applies this also when it ends without recording anything (a registry entry that does not change, a server that no target takes): an existing lock whose line has to come or go is then written whole, like every other lock, and one that already agrees is not touched. The lock has the line when the document has a top-level `apm_version` key, whatever its value or quoting. A user who declines to replace an entry changes no file. Deviation: the Oracle has no such flag and does not add a missing line. A lock in the format before issue #50 is read without error: a frozen install uses it as it is, every other install, and `update`, writes it again in the current format and removes the `apm_modules/` directory the old lock named. A dependency that is a directory of a repository (an entry with a `virtual_path` that is a directory) records as `resolved_commit` the commit of the repository it was taken from, whether or not the project is itself in a git repository, and a frozen install fetches that commit. Such an entry has no `tree_sha256`, as in the Oracle's lock: its content is pinned by the commit and by `deployed_file_hashes`. Deviation from the project's own spec: `req-lk-015` asks for a `tree_sha256` on every git source. A lock written before issue #65 for a project inside a git repository records the project's own commit for such an entry, with a `tree_sha256`; a frozen install of it fails at the download, and an `install` that is not frozen writes the right commit. The other entry fields of git and registry sources were ported from the Oracle's source and have not been measured against it.
- Frozen install (`install --frozen`, and `install` under CI): the deployed files are checked against the hashes in `apm.lock.yaml`. A recorded file that is on disk with other content is an error with exit 1, and the file is not overwritten. When the only differences are recorded files that are not on disk (a fresh clone), they are deployed from the lock and the install ends with exit 0; this needs `apm.yml`, a target, and a target that governs each such path, and without a target the exit code is 2. A deploy whose result is not what the lock records, because a source changed after the lock was written or has a file the lock does not have, is an error with exit 1, decided on a trial deploy in a temporary directory: the deploy root is left as it was, and only the package sources fetched into `apm_modules/` stay. No frozen install writes `apm.lock.yaml`, `apm.yml` or `.gitignore`. Deviation: the Oracle's `--frozen` checks only that the lock pins every dependency and then runs an ordinary install, so in these cases it overwrites the changed file or rewrites the lock, and exits 0.
- Local-path packages: the package is copied to `apm_modules/_local/<directory name>` and the lock records `repo_url: _local/<directory name>`, `source: local` and `local_path`, as the Oracle does. `install <local path> --skill` writes the `apm.yml` entry as `path:` with `skills:`, as the Oracle does. In `apm.yml` the object form `- path: <value>` takes the same values as the string form and reads the same path; `- path: dep` is refused with the Oracle's reason text and exit 1, and no file is changed. As in the Oracle, a path that starts with `//` and a UNC path (`\\host\share`) are refused in both forms, and whitespace around a path is dropped in both, so `- './dep '` is `./dep`; when `install <local path> --skill` writes the entry, the path it writes has no whitespace around it either. As in the Oracle, a path above the project root (`../dep`) is taken in both forms and by `install ../dep`, which writes `- ../dep`, and a path whose last component is not a name (`./`, `./.`, `./dep/..`, `/`, `../`) is refused in both forms with exit 1 and the Oracle's text `Local path '<path>' does not resolve to a named directory. Use a path that ends with a directory name (e.g., './my-package' instead of './').` The text before the reason is apm-go's own (for `install`: `validate apm.yml: dependency entry <N> (path: "<value>"): ...`). As in the Oracle, a symlink in a local package that resolves inside the package is copied as the file or directory it points at, so `.apm/agents -> ../agents` deploys the agents; a symlink that dangles, resolves outside the package, or leads back to a directory it is in ends `install` with exit 1 and the Oracle's reason text (`Symlink '<path>' resolves to '<target>', which escapes the package root '<package>'. ...`; a symlink loop is the reason `Symlink loop from '<path>'` alone, and a file or directory of the package that cannot be read has the Oracle's text too, with Python's `[Errno <n>] <message>: '<path>'`), and neither `apm_modules/_local/<name>` nor an `apm_modules/` the install created stays; the text before the reason is apm-go's own. The Oracle leaves an empty `.claude/` after such a failure, apm-go does not. Deviations: two local packages with the same directory name end `install` with an error before anything is written (the Oracle copies the second over the first and exits 0); a local package is refused before the resolve, with exit 1 and no file written, when its directory is the project directory or a directory above it (`../proj`, the project's absolute path; the Oracle copies the project into itself until `File name too long`, exits 1 and leaves `.claude/` behind), when its copy `apm_modules/_local/<name>` resolves, through a symlink at any of its components, the last one included, to a place outside `apm_modules/` (the Oracle refuses it too, during the install, with the reason of the next item), or when its directory and its copy overlap once symlinks are resolved; an `alias` the entry already has stays after `install <local path> --skill` (the Oracle drops it); `install <local path>` with no skill subset to write does not rewrite an entry that already exists, so a value with whitespace around it stays as written (the Oracle rewrites the entry; one case of ticket 32 item 18). A local package that declares a local package of its own is refused, and the refused copy does not stay in `apm_modules/`.
- A package directory below `apm_modules/` is removed or written only when, every symlink on its path resolved, the last component included (a dangling one by its target), it is still below `apm_modules/` with that directory's own symlinks resolved, and is not `apm_modules/` itself, as in Oracle 0.33.0. A symlinked `apm_modules/` passes, and so does a directory that does not exist yet. This holds for `uninstall`, `uninstall --global`, `install`, `install --global`, a frozen install and `update`, for a local copy, a git checkout, a directory of a repository and the extraction of a registry package. `uninstall` checks every directory it would remove before it writes anything; the first one that fails ends it with exit 1 and two lines, and no file changes, `apm.yml`, the lock, the deployed files and `apm_modules/` included: ` x Refusing to remove <key>: Cannot verify containment of '<abs>' within '<base>': Path '<abs>' resolves to '<resolved>' which is outside the allowed base directory '<base>'` (for a transitive package `Refusing to remove transitive dep <key>: ...`) and ` x Uninstall incomplete: package deletion failed. apm.yml and lockfile ownership were retained; some package files may already have been removed. Resolve the unsafe package path and retry the same uninstall command, or run 'apm-go install' to restore the declared packages. Run with --verbose for detailed diagnostics.` (`'apm-go install --global'` for `--global`). `uninstall --dry-run` exits 0 and leaves out the `from apm_modules/` line of such a package. `install`, a frozen install and `update` end with one error line and exit 1 before the directory is removed or written, and do not write `apm.lock.yaml`, `apm.yml` or `.gitignore`; the line of a git or registry package holds the same reason, the line of a local package is the local-path refusal above. Deviation: when it refuses a transitive package, the Oracle has already removed the directories of the direct packages; apm-go removes nothing.
- A deployed path is removed, replaced or written only when each directory on it, every symlink resolved, is below its target root (the path's first component below the deploy root: `.claude`, `.github`, `.agents`, `.codex`, `.opencode`), with that root's own symlinks resolved. The deploy root is the project for a project command and `HOME` for `--global`. Where the path's content is written or the path is made (a copied file, a converted rule, agent or `plugin.json`, each file and directory of a copied skill, each file and directory the `uninstall` hand-over makes), the path itself, every symlink resolved (a dangling one by its target), has to be below the target root too, because a write, and the making of a directory, follows a symlink at the last component; a deployed file that the user replaced by a symlink out of the target root is therefore not written through. Where the last component itself is removed or replaced (a cleanup, a symlink deploy), it is not resolved, nor is anything below a symlink at a skill's directory (`skills/<name>`, see the item on a skill directory the user replaced by a symlink). A target root linked elsewhere (`~/.claude` or the project's `.claude` linked into a dotfiles directory) passes, and a deployed file that is a symlink to another place in its target root (`.claude/rules/r.md -> ../shared/r.md`) is written where it points. This holds for `uninstall`, `uninstall --global`, `install`, `install --global`, a frozen install and `update`, for every file, skill directory and symlink the deploy writes and every one a cleanup removes. `uninstall` checks every deployed path of the packages it removes, and the tree of every skill directory one of them is in (walked without following a symlink, a skill directory that is itself a symlink not walked), before it writes anything, because a skill passes as a whole to a package that stays, with files the removed package does not have; when one fails it ends with exit 1, changes no file (`apm.yml`, the lock, the deployed files and `apm_modules/` included), and prints after its ` > Uninstalling ...` and ` + ... found in apm.yml` lines: ` x Uninstall could not remove tracked target files; manifest and lockfile ownership were preserved. Package directories may already have been removed.`, one ` x   - <path>` per failing path, per recorded skill directory with one below it, and per such skill directory whose tree holds a symlink that resolves (a dangling one by its target) out of the target root, sorted, and ` x Resolve or remove the listed files, then retry uninstall.` A stale path of `install`, `update` or `install --global` that fails is the user's: it stays, one warning names the symlink (` ! keeping "<dir>": it is a symlink to <resolved>, outside <target root>, so nothing below it is removed`), it is dropped from the lock, and the exit code does not change. A destination that fails is not written, nothing there is removed, and that primitive's deploy fails with the warning ` ! deploy <name> to <target> failed: <path>: symlink <link> resolves to <resolved>, outside <target root>` (`<link>` is the directory that leads out, or the path itself), as any failed deploy does: the exit code does not change, the bucket is not cleaned and keeps its old lock record, and a frozen install ends with exit 1 on the violation of that path. Deviations: when Oracle 0.33.0 refuses an uninstall for this, it has already removed the packages' directories under `apm_modules/` and the paths it could remove; apm-go removes nothing. The Oracle refuses a target root that is a symlink too (`integration/base_integrator.py:506-590`); apm-go allows it, as the `--global` cleanup has. The Oracle's stale install keeps such a path without a warning. Where a deploy's destination fails, Oracle 0.33.0 ends `install` with exit 1 and changes no lock, and apm-go warns and exits 0; through a symlinked directory the Oracle has by then written the file where the link points, also over a file of the user's that is there, and ends with `Cannot translate ... to a lockfile path` (measured), where apm-go writes nothing. The Oracle bounds a destination by the primitive's own directory (`.claude/rules`, a skill's directory), not the target root, so it also refuses a deployed file linked to another place in `.claude`, which apm-go writes, and an `uninstall` whose skill directory holds a symlink to another place in `.claude`, which apm-go hands over through it (measured).
- `install`, `uninstall` and `install --mcp` print the Oracle's success transcript. Deviation: apm-go does not print the Oracle's two `Skipped inactive experimental resolver for target ...` lines. The directories the Oracle leaves empty (`apm_modules/` after `uninstall`, `.claude/` after `install --mcp`) are left too; the Oracle's cache directories under `~/.cache/apm/` are not created. A runtime failure of `install` or `update` is one error line, with no usage text.
- `compile`: `AGENTS.md` has the Oracle's format. Deviations: apm-go writes only the root `AGENTS.md` and does not distribute instructions into subdirectories, and its terminal text is its own short transcript, not the Oracle's analysis and placement table.
- Instruction `applyTo` (issue #76): an instruction's frontmatter is read as YAML, as Oracle 0.33.0 reads it with PyYAML's YAML 1.1 rules. A block or flow list is one value: its items joined with `,`, a null item and one that is blank once stripped left out, and a comma outside `{...}` and a `[...]` class or a backslash in an item escaped (`\,`, `\\`). A value that is not a string is Python's `str()` of it (`yes` is `True`, `0x1F` is `31`, `1e3` stays `1e3`, `[x, 1]` is `['x', 1]`); a null, an empty string and an empty list are no `applyTo`. `install` writes each glob of the value as one item of `paths:` in `.claude/rules/<name>.md`: the value is split at each comma outside `{...}` and a `[...]` class, `\,` and `\\` are a comma and a backslash, each glob is stripped, and it is written as `json.dumps` writes it (non-ASCII as `\uXXXX`); a value with no glob gives a rule with no frontmatter. `compile` groups instructions by the joined value (`` ## Files matching `src/**/*.ts,web/**/*.ts` ``). The other targets copy the instruction as it is. Deviations: a frontmatter that is not valid YAML (an unquoted `applyTo: **/*.go`, an alias in YAML) or that PyYAML refuses fails that one claude rule with ` ! deploy <name> to claude failed: <path>: frontmatter: <reason>`, exit 0, the old rule and its lock record kept, where Oracle 0.33.0 ends `install` with exit 1 (`Rejected frontmatter in ...`); `compile` skips such a file with ` ! Skipping <path>: frontmatter: <reason>` and compiles the others, as the Oracle does with its own text, and an instruction of the same name from a dependency takes its place. `compile` skips a file it cannot read or that is not valid UTF-8 the same way, before same-name conflicts are resolved, and the exit code stays as it is: a project file is reported (` ! Skipping <path>: <reason>`); a dependency's file is skipped without a word when it cannot be read or its first 8192 bytes do not decode (a sequence those bytes cut short does not count), and reported otherwise, as Oracle 0.33.0's discovery does. Before issue #76 a project file that could not be read ended `compile` with exit 1, and a file that was not valid UTF-8 was compiled; `install` is not changed by this. A frontmatter with an anchor, an alias or a merge key is refused the same way (the OpenAPM safe subset), where the Oracle reads it, and so is an explicit tag the YAML 1.1 resolver would not give the value (`!!float 1`, `!!binary`, `!!set`, `!!omap`, `!!pairs`), which the Oracle converts. A mapping value whose keys are not all strings is written as Python's `repr()`, where Oracle 0.33.0's `install` ends with exit 1 (`'<' not supported between instances of 'str' and 'int'`).
- `marketplace init`: the Next Steps panel has the Oracle's layout. Deviations: the template's commented example says `# ref: v1.0.0` (`pack` rejects a branch ref), and the text says `apm-go pack`.
- Symlinks in a dependency (a package under `apm_modules/`: a git repository or a directory of one; issue #89): a symlink that resolves inside the package is followed, and what it points at is deployed under the symlink's own name. A symlink that resolves outside the package, does not resolve, or loops ends the command with exit 1 before anything is deployed: nothing under the deploy root outside `apm_modules/` changes, and `apm.lock.yaml`, `apm.yml` and `.gitignore` are not written. The error line names the dependency, the symlink's path in the package, and what it resolves to or why it does not (` x deploy: dependency <key>: symlink <path> resolves to <target>, outside the package`). This holds for `install`, `install --global`, a frozen install, `update` and `compile`. A dependency's `apm.yml` that leaves the package fails `install` and `update` while they resolve; `uninstall` reads it as a missing file, so the package can still be removed. While a directory of a repository is taken out, the package is the whole repository, and a failed extraction leaves no copy in `apm_modules/`. A component path that `.claude-plugin/plugin.json` declares through a symlink is skipped, as before. The project's own `.apm/` is not covered: its symlinks are deployed as before. Deviation: Oracle 0.33.0 copies a git dependency out of its cache with every symlink resolved, so it deploys the content from outside the package and exits 0; with `APM_NO_CACHE=1` it skips a source with a symlink on its path (with a warning for an agent). For a directory of a repository, both refuse a symlink that leaves the repository.
- A skill directory the user replaced by a symlink: while the package still has the skill, `install` replaces the symlink by the skill (a directory for a project, the deploy's own symlink for `--global`) and writes nothing through it. Once the skill is gone from the package, or at `uninstall`, the symlink is the user's: nothing is deleted through it, also a file with the same bytes as the package's, it stays, one warning names it, and `install` drops its paths from the lock, so the warning is not repeated and a frozen install and `audit` do not check the user's files. For `--global` this holds for a symlink pointed outside the package it was deployed from; the same goes for an agent or command symlink. A symlink on a directory above the skill's, below the target root (`.claude/skills` linked elsewhere), or inside the skill's directory, is covered by the item on deployed paths instead.
- `uninstall`: a file that a package which stays also deploys is left on disk when the package that owned it is removed, with the content of the package that stays, and the lock records it under that package; a shared skill passes as a whole directory, with every file the package that stays has in it and none of the removed package's own; the same holds for `--global`. Oracle 0.33.0 picks the owner of a shared file in its own way (measured: of two local packages that share a rule, the one declared second, where apm-go picks the first; of `microsoft/apm-sample-package` and a local copy of its files, the sample in both); when the removed package is not the owner Oracle picked, the result is the same. Deviation: when the removed package is the owner Oracle picked, Oracle deletes the file, deploys the package that stays to other targets (`.github/`, `.agents/skills/`), and records nothing for it in the lock; apm-go keeps the file and records it under the package that stays. Between the `Updated <apm.yml>` line and `Uninstall complete`, each package that stays and received a file gets the lines of its install block with no header (`|-- 1 rule(s) adopted -> .claude/rules/`), as the Oracle prints them. Deviation: the Oracle prints such lines for every package it deploys again, also one that shares no file with the removed package; apm-go prints them only for a package that received a file, so an `uninstall` that hands nothing over prints what it printed before. A local package can also be removed by its lock name `_local/<name>`: when the lock has an entry with `source: local` and `repo_url: _local/<name>` whose `local_path` is a path `apm.yml` declares, the result is that of removing that path, also for `--global`, as in Oracle 0.33.0. When the name matches more than one declaration (one path declared twice, in one section or in both, or two paths that share the lock name), `uninstall` prints the Oracle's ` x Ambiguous dependency '<name>': it matches <N> declarations. ...` for each such argument and ` x Uninstall aborted: <M> requested package(s) could not be selected. ...`, exits 1 and changes no file, also with `--dry-run`. A package that several arguments select gets one `found in apm.yml` line per argument and is removed and counted once, as in the Oracle. Each argument's line (`found in apm.yml`, `not found in apm.yml`, `Ambiguous dependency`) comes in the order of the arguments, as in the Oracle; the `Uninstall aborted` line follows the last of them. What resolving a marketplace argument says (`could not resolve`, `cannot preview with --dry-run`, the supply-chain refusal) comes before every argument's line, as in the Oracle, which resolves those arguments first; between several of them apm-go keeps the order of the arguments, where the Oracle's order changes from run to run. Deviations kept by ruling: a package that is not installed is a warning with exit 0 (the Oracle exits 1), and `uninstall <MCP server name>` removes that server (the Oracle rejects the name). `uninstall` deletes `apm.lock.yaml` only when it records nothing and has no top-level key apm-go does not model; a lock with such a key (`x-*`, `lsp_*`, `mcp_config_provenance`, any unknown key) stays, with `dependencies: []` and those keys as they were (the Oracle deletes it).

## Product Principles

1. **Output is a contract.** Words, bytes, exit codes, and file trees are gated in CI; an unrecorded difference is a bug until a waiver names it.
2. **Additions are opt-in supersets.** New flags and commands default to the existing behavior and are documented at their site in code.
3. **One vocabulary on every stream.** Status symbols, framing, and wording are the same in interactive, piped, and CI output; the ux layer, not call sites, decides presentation.
4. **User files are sacred.** `apm.yml` and context files are patched, never rewritten. The lockfile is machine-written in one layout, the Oracle's, and keeps every key it does not model.
5. **Fail closed.** Unknown security policy blocks; unknown waiver IDs fail the gate; unsafe YAML is rejected.
