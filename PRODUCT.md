## Platform

web

The web platform covers the documentation surface (confirmed 2026-08-29). The product's other confirmed surface is the CLI's own terminal UI (`internal/ux/`), which is not a web/native platform: any work there is governed by the terminal constraints in Operating Context, not by web design guidance.

## Users

- **AI-agent users / developers** (primary): run `apm-go init`, `install`, `compile`, `update`, `uninstall`, `audit` inside their own repositories to produce and maintain the root context files AI agents read on startup (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) and to manage package + MCP-server dependencies declared in `apm.yml` / `apm.lock.yaml`.
- **Marketplace / plugin authors** (primary): run `marketplace init`, `marketplace package add`, `marketplace audit`, `plugin init`, `pack` to author a marketplace, package skills/instructions, and publish Claude Code plugins (`marketplace.json`, `plugin.json`, `.mcp.json`).

Both audiences work in a terminal, frequently non-interactively (CI, agent-driven shells). Other audiences (platform / CI teams) exist in practice but were not confirmed as primary.

## Product Purpose

apm-go is an Agent Package Manager shipped as a single static Go binary with no interpreter or runtime dependency. It compiles `.apm/` primitives (instructions, agents, chat modes, memory) into agent context files, installs/uninstalls packages and MCP server configurations from marketplaces, and packages plugins for distribution.

Success: a user gets deterministic files, output, and exit codes from one binary installed via `install.sh` or a GitHub release, with no runtime to set up.

## Positioning

**Single static binary + a tested, extended command surface.** Output bytes, exit codes, and generated file trees are kept stable and pinned by apm-go's own tests (`go test`, `tools/realexec.sh`), so scripts and agents can depend on them. The upstream Python implementation (the Oracle) is the reference design apm-go starts from; apm-go follows it where that serves its users and differs where it has a reason to. On that base apm-go ships its own additions — `pack --claude-source-style url`, `pack --json`, `--check-versions` / `--check-clean` release gates, top-level `doctor`, `normalize`, `validate`, `marketplace package update` — each documented at its site in `cmd/apm-go/*.go`. Upstream additions are ported when apm-go chooses to; `pack --strict-metadata`, the read-only `pack --check-clean`, and the Git URL rewrite safety check came from upstream 0.29.1.

## Operating Context

- Runs in a terminal; output goes through `internal/ux/`, which auto-detects TTY, `NO_COLOR`, and CI (`CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `BUILDKITE`, `TF_BUILD`, `JENKINS_URL`). Non-TTY/CI disables spinners and prompts; `NO_COLOR` disables color but **not** prompting.
- `ux.Error` / `ux.Warn` always land on stdout.
- Under CI, `install` defaults to frozen (lockfile-only) mode.
- A user's `apm.yml` is a hand-edited file; every mutation is a round-trip patch that preserves comments, ordering, and formatting. `apm.lock.yaml` is written whole in the Oracle's layout (issue #50): keys apm-go does not model survive, comments and the quote style of the old file do not.
- Git is a subprocess run under a hardened environment (no credential prompts, transport allow-list). On this project's development machine there is no SSH key, which is why `--claude-source-style url` exists for installable marketplaces.
- Distribution: `install.sh` (defaults to latest stable; pre-release tags are GitHub prereleases), GitHub Releases, mise (`github:gn00678465/apm-go`, through its `github` backend), `go build`. The release version is injected from the git tag at release build time (`internal/version/version.go`); local builds report `dev`.

### Terminal UI design

Presentation rules the CLI's own terminal output follows. Words, order, exit codes, and generated files are not presentation and are not covered here.

**Status symbols.** Every status line starts with one centered, colored, width-3 symbol from the single vocabulary in `internal/ux/colors.go`. Brackets are never printed, on any stream, interactive or piped.

| class | symbol |
|---|---|
| success | ` + ` |
| info | ` i ` |
| warning | ` ! ` |
| error | ` x ` |
| progress | ` > ` |
| list | ` * ` |
| plan diff update / remove / unchanged | ` ~ ` ` - ` ` = ` |

Call sites never choose a glyph; they call the `ux` printer for the class (`ux.Success`, `ux.Info`, `ux.Warn`, `ux.Error`, `ux.Progress`, `ux.List`). `ux.Plain` is for complete rows or text without a status symbol. Mixing symbol styles across commands was an earlier defect; one vocabulary is the fix.

**Interactive `init` / `plugin init`.** The interactive session is rendered as one clack-style transcript on stderr (`ux.NewClack`, `cmd/apm-go/init.go`): the prompts, an "About to create" note, a "Created project directory" progress line, and a single "Initializing" note that holds the success content (title, Created Files table, Next Steps, tips). Rules that must hold:

- the left frame border is continuous — no glyph or box line starts at column 0 inside the frame;
- status symbols inside the frame are the project symbols above;
- notes are capped to terminal width and wrap (`Clack.Note`), so a wide terminal or a long path never breaks the layout;
- consecutive steps keep a blank spacer line so a note does not sit directly against the previous prompt;
- the non-interactive path (`--yes`, non-TTY, CI) prints the same success content as plain status lines with the same symbols;
- `plugin init` shares the same core (`runInitCore`) and the same frame; it has its own flag set (`--verbose`, `--format`, `--claude-plugin`) and does not carry consumer init's `--force`;
- no docs/star footer is printed after the success block.

## Capabilities and Constraints

Command surface (`apm-go --help`): `audit`, `compile`, `completion`, `deps` (list/tree), `doctor`, `experimental`, `init`, `install`, `marketplace` (add/list/browse/update/remove/validate/init/package/audit), `normalize`, `pack`, `plugin` (init/validate), `search`, `self-update`, `uninstall`, `update`, `validate`.

Constraints future work must preserve:

- Output contract: words, exit codes, output bytes, and file trees are what apm-go's own tests pin (`go test`, and `tools/realexec.sh` for full stdout, stderr, exit code and file tree); a change to them is made on purpose, and one an existing user sees after upgrading goes into the release notes. The Oracle is a reference, not a gate: `tools/parity` compares apm-go with an Oracle release when it is run by hand, and a difference it reports is information, not a bug by itself. The `Deviation:` notes and owner rulings in the items below record past decisions; a new difference needs no ruling.
- Exit codes: usage errors are 2; specific codes via `withExitCode()`. `pack` exits 3 for a failed `--check-versions`, 4 for a failed `--check-clean`, and 5 for a failed `--strict-metadata`; 5 is decided before any producer runs, and 3 wins over 4.
- JSON bytes from pack/scaffold go through `bundle.MarshalIndent` (2-space indent, non-ASCII escaped as `\uXXXX`); the marketplace builder alone emits UTF-8 unescaped.
- YAML ingestion is restricted to the OpenAPM safe subset (no anchors, merge keys, custom tags) — `spec/conformance/openapm-v0.1.md`.
- Marketplace metadata certification (`pack`): each resolved package has one metadata outcome (`fetched`, `empty`, `failed`, `offline`, `local`, `explicit`), reported in `pack --json` as `metadata_enrichment`. Only the Claude output uses package metadata. `--strict-metadata` fails with exit 5 before anything is written when a selected output's metadata could not be fetched. `--check-clean` is always read-only (it implies `--dry-run`), reuses the metadata of the same run, and reports an output whose metadata could not be fetched as `uncertifiable` (exit 4) without comparing it. An outcome's cause never carries raw error text, a URL, or a credential.
- `pack --force` over a plugin manifest that is a symlink (measured for `.claude-plugin/plugin.json -> ../custom.json`): apm-go replaces the symlink with a regular file that holds the generated manifest and leaves the file it pointed at as it was, because its write is a temporary file renamed over the path and never follows a symlink. Deviation: Oracle 0.33.0 keeps the symlink and writes the manifest into the file it points at (`core/plugin_manifest.py:482`, `utils/atomic_io.py:40-48`, `Path.write_text`) (issue #88 batch ruling, item 59).
- Git URL rewrite safety: before every network git subprocess, apm-go reads the effective `url.*.insteadOf` rules and refuses a rewrite that downgrades the transport, adds credentials, or moves an authenticated remote to another host or origin; a config that cannot be read fails the operation instead of being skipped.
- Credential scanning (`internal/security/`) runs in `pack` (warn policy) and `audit` (report); its policy gate is fail-closed (unknown policy = block). It is not part of install/deploy.
- Deploy targets: claude, codex, copilot, antigravity, opencode, agent-skills (adapter per target). Deviations: `--target hermes` is refused with ` x --target "hermes": unknown target "hermes"`, the usage text and exit 2, because apm-go has no hermes adapter, where Oracle 0.33.0 takes it (`manifest_target_names`, `core/target_catalog.py:258-266`; measured: `install ./pkg --target hermes` exits 0 and writes `hermes` under `targets:`); the `Accepted values` comment of `apm.yml` still lists `hermes` (issue #88 batch ruling, item c46-1). `targets: [agy]` in `apm.yml` is antigravity, where Oracle 0.33.0 ends `install` with exit 2 and `Unknown target 'agy'` (measured), because the names its `apm.yml` takes have no alias (`core/target_catalog.py:258-266`), while `--target agy` is antigravity on both sides (`aliases=("agy",)`, `core/target_catalog.py:167`) (issue #88 batch ruling, item c62-4).
- `devDependencies.mcp` (issue #97): the MCP servers `apm.yml` declares there are configured by `install`, `install --global`, a frozen install and `update` as those of `dependencies.mcp` are, with the same output, config files and lock records, as in Oracle 0.33.0. The servers of `dependencies.mcp` come first, and of two servers with one name the first declared is configured. A dependency's own `devDependencies.mcp` is not configured, as in the Oracle. Before issue #97 apm-go configured none of them and printed nothing about them.
- Codex MCP config: a server entry in `.codex/config.toml` has no `id` field, because Codex's config schema has no such field and `--strict-config` rejects the file over it. Deviation: the Oracle writes `id = ""` on stdio and http entries (upstream microsoft/apm#3087). A new `install` drops an old `id` from the entries apm-go manages; an entry for a server that is no longer in `apm.yml` is removed whole when the old lock records the server (see Stale MCP servers), and is not touched otherwise.
- MCP `enabled`: the value an `apm.yml` MCP entry declares for `enabled` is written to `opencode.json` as it is, whatever its type (`true` when the entry has none), and recorded in the lock's `mcp_configs`, for a self-defined and a registry server and whatever the targets. It is read as the Oracle's YAML 1.1 loader reads it: a plain `no`, `off` or `False` is `false`, a quoted one a string. The config files of the other targets do not carry it, as in the Oracle. A change of the type of `enabled` alone (`false` to `'false'`, `false` to `0`) is a change: the lock is written again and `install` prints the server as updated. No other field of a server is compared by type, so an Oracle lock that records an integer in `args` or `env` stays as it is. Deviation: the Oracle compares `false` and `0` as equal and keeps its old lock.
- Stale MCP servers (issue #71): `install`, `install --global` and `update` remove from the MCP config files a server that the old `apm.lock.yaml` records and that is no longer declared or no longer goes to a target, before the lock is written, as Oracle 0.33.0 does. A registry that refuses or does not answer ends the install and removes no stale MCP server (see the item on the MCP registry). When MCP servers are declared, a target that is no longer active (a `targets:` in `apm.yml` or a `--target` that no longer names it) loses every server the old `mcp_target_servers` lists for it, then every active target loses each server of the old `mcp_servers` that is no longer declared. A lock with `mcp_servers` and no `mcp_target_servers` (apm-go v0.3.0) gives the first rule nothing, as the Oracle's legacy adoption does for a lock with no `mcp_configs`. The file is the one `install` writes, below the project or, for `--global`, `HOME`. Other servers and keys of the file stay, and the file is written the way `install` writes it, so in a JSON file other than `.mcp.json` the keys come out sorted and `.codex/config.toml` is rendered again; a file that has none of the names is not written. Deviations: the Oracle cleans `.mcp.json` only when `.claude/` is a directory and `opencode.json` only when `.opencode/` is one, and apm-go cleans both whatever the directories, because it writes `opencode.json` without making `.opencode/`; a name with a `/` is removed as written and not also by the part after the last `/`, because apm-go keys every entry by the full name; copilot's file is `.github/mcp-config.json` in a project and `~/.copilot/mcp-config.json` for `--global`, the other `--global` files are apm-go's own; a recorded target that is not one of apm-go's MCP targets (claude, codex, copilot, antigravity, opencode), such as the Oracle's `cursor`, is skipped; a frozen install cleans nothing, because it writes no lock; the Oracle keeps the key order of a JSON file it cleans.

## Product Principles

1. **Output is stable.** Words, bytes, exit codes, and file trees change only on purpose, and a change an existing user sees is recorded in the release notes. The Oracle is the reference design, not a gate.
2. **Additions are opt-in supersets.** New flags and commands default to the existing behavior and are documented at their site in code.
3. **One vocabulary on every stream.** Status symbols, framing, and wording are the same in interactive, piped, and CI output; the ux layer, not call sites, decides presentation.
4. **User files are sacred.** `apm.yml` and context files are patched, never rewritten. The lockfile is machine-written in one layout, the Oracle's, and keeps every key it does not model.
5. **Fail closed.** Unknown security policy blocks; unsafe YAML is rejected.

- Terminal output must remain meaningful without color (`NO_COLOR`) and without a TTY (CI, pipes); status is carried by the symbol glyph, not color alone.
